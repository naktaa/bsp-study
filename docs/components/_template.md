# 컴포넌트 이름: 한 줄 설명

지금 어떻게 돌아가는지, 어디를 고치는지, 문제가 생기면 어떻게 조치하는지를 적는 운영 문서다. 왜 이렇게 만들었는지는 학습 문서에 둔다. 150줄 안팎으로 쓰고 코드 블록은 30% 이하로 둔다.

## 1. 요약
- **역할:** 시스템에서 하는 일 한 줄
- **상태:** 동작 확인한 것 / 미검증 한 줄 (상세는 학습 문서 6장)
- **담당 파일:** 드라이버·overlay·레시피·config 링크
- **학습 문서:** [learning/NN](../learning/NN-주제.md)

## 2. 구성
흐름 한 줄: `HW → DT → driver → subsystem → user`

| 항목 | 64GB 카드 (6.18.59 Debian) | Yocto 카드 (6.6.63) |
| --- | --- | --- |
| HW 연결 | 핀·주소 한 줄 ([bringup](../bringup.md#앵커)) | 같음 |
| DT/overlay | | |
| 드라이버 | 직접 작성 / 업스트림 | |
| 커널 config | | |
| 사용자 인터페이스 | `/dev`, sysfs | |

- 사양은 [hardware.md](../hardware.md), 배선은 [bringup.md](../bringup.md)에서만 관리한다. 여기에는 한 줄과 링크만 둔다.
- 두 카드가 다른 점(compat 헤더, 자동 적재, config 위치)은 표에서 칸을 나눠 드러낸다.

## 3. 빌드·배포
- **64GB 카드:** WSL 빌드 → scp → insmod/dtoverlay

```bash
# [WSL] ~/bspworkspace/bsp-study — 선행 조건 한 줄
```

- **Yocto 카드:** 어떤 레시피가 빌드하고 어떻게 자동 적재되는지 1~2줄

```bash
# [WSL, Yocto] ~/yocto/build — 선행 조건 한 줄
```

## 6. 트러블슈팅
계층 번호는 [공통 점검 순서](README.md#공통-점검-순서)를 따른다. 이 컴포넌트에서 의미 있는 계층부터 본다.

| 계층 | 증상 | 먼저 확인 | 원인 | 조치 |
| --- | --- | --- | --- | --- |
| 4 모듈 적재 | | | | 한 줄 또는 [조치 절차](#조치-절차-짧은-이름) |

- 표는 색인이다. 한 줄로 끝나는 조치는 표에 쓰고, 순서가 있는 복구·조치는 아래 "조치 절차"로 링크한다.
- 실제로 겪은 사례만 쓴다. 겪지 않았지만 자주 날 만한 문제는 표 아래 "점검 포인트"에 2~3줄로만 둔다.

### 조치 절차: 짧은 이름
1. 무엇을 확인하고
2. 무엇을 바꾸고
3. 어떻게 정상인지 본다

```bash
# [Pi] 실행 위치 — 목적 (3~5줄)
```

**점검 포인트**
- 겪지 않았지만 볼 곳 한 줄
