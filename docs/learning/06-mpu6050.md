# MPU6050: 센서 FIFO·IRQ·커널 큐로 사용자에게 전달

## 1. 한눈에 보기
- **목적:** I2C 센서 드라이버를 직접 써서 probe, 레지스터 설정, IRQ, 버퍼링, 사용자 전달이 어떻게 이어지는지 이해한다. 이 구조는 다음 단계 [IIO 문서](09-iio-direct.md)와 비교하는 기준이 된다.
- **기능:** GPIO17 Data Ready IRQ가 오면 센서 FIFO의 6축 패킷을 읽어 커널 큐(128개)에 넣는다. 앱은 `/dev/mpu6050`에서 blocking read로 한 샘플씩 받아 g·deg/s로 출력한다.
- **직접 작성 / 가져다 쓴 것:** 센서 드라이버·overlay·앱은 직접 작성했다. I2C 컨트롤러(`i2c-bcm2835`)·GPIO IRQ·misc 코어는 커널 것을 쓴다.
- **결과(실측):** 흔드는 상태에서 앱이 20개를 연속 수신했다(Skip 0, 단절 0). 제거 시 FIFO 넘침·리셋·큐 넘침 모두 0. 상세는 [6장](#6-트러블슈팅과-한계).
- **범위 밖:** 타임스탬프, 카메라 동기화, 보정·각도 추정. 타임스탬프는 09 IIO 단계에서 다룬다.
- **관련 파일:** [mpu6050_drv.c](../../examples/mpu6050/mpu6050_drv.c), [mpu6050_data.h](../../examples/mpu6050/mpu6050_data.h), [mpu6050_app.c](../../examples/mpu6050/mpu6050_app.c), [mpu6050-overlay.dts](../../examples/mpu6050/mpu6050-overlay.dts), [Makefile](../../examples/mpu6050/Makefile), 배선은 [bringup](../bringup.md#gy-521-배선)

## 2. 구조

**한 샘플의 흐름:** 센서 FIFO → INT(GPIO17) → `mpu6050_irq_thread` → `mpu6050_drain_fifo`(I2C) → 커널 큐 → `read()` → 앱

```text
 +-----------+  INT / GPIO17   +------------------+  queue_packet  +--------------+  read()  +-------------+
 |  MPU6050  |---------------->|  irq_thread      |--------------->| kernel queue |--------->| mpu6050_app |
 |  FIFO 1KB |<----------------|  drain_fifo      |                | 128 samples  |          | g, deg/s    |
 +-----------+  I2C FIFO_R_W   +------------------+                +--------------+          +-------------+
```

센서는 10ms마다 12바이트 패킷을 자기 FIFO에 쌓는다. IRQ 스레드는 그때까지 쌓인 완전한 패킷을 모두 읽어 커널 큐로 옮기고, 잠든 read를 깨운다.

| 계층 | 구성 요소 | 하는 일 |
| --- | --- | --- |
| 하드웨어 | MPU6050, GY-521 | 100Hz 측정, 센서 FIFO 적재, INT 핀 출력 |
| DT | `mpu6050-overlay.dts` | I2C1 0x68 장치 선언, GPIO17 level-high IRQ, 풀다운 |
| 커널 버스 | `i2c-bcm2835`, I2C 코어 | compatible 매칭 후 probe 호출, SMBus 전송 |
| 직접 작성 드라이버 | `mpu6050_drv.ko` | 센서 설정, IRQ 처리, FIFO drain, 커널 큐, misc read |
| 사용자 공간 | `mpu6050_app` | 16바이트 구조체 read, 단위 환산, 단절 표시 |

## 3. 알아야 할 개념

### 왜 센서 FIFO와 커널 큐가 둘 다 있는가
지연이 생기는 곳이 두 군데이기 때문이다. 센서 FIFO는 **CPU가 IRQ를 늦게 처리할 때** 측정값을 잡아 두고, 커널 큐는 **앱이 늦게 읽을 때** 전달할 값을 잡아 둔다. FIFO를 쓴다고 지연이 늘지는 않는다. 찰 때까지 기다리지 않고 IRQ마다 쌓인 만큼 가져오기 때문이다([drain_fifo L225](../../examples/mpu6050/mpu6050_drv.c#L225)).

### 왜 threaded IRQ로 받는가
I2C 전송과 `mutex_lock`은 잠들 수 있어서 hard IRQ 문맥에서 호출하면 안 된다. 그래서 primary handler는 NULL로 두고 실제 일은 스레드에서 한다. `IRQF_ONESHOT`은 스레드가 끝날 때까지 같은 IRQ를 막아 재진입을 방지한다([request_threaded_irq L552](../../examples/mpu6050/mpu6050_drv.c#L552)).

### 왜 level-high + 래치로 맞췄는가
칩의 INT 출력 방식과 GPIO가 IRQ로 인식하는 조건은 짝이 맞아야 한다. 칩은 INT_PIN_CFG=0x20(active-high, 래치)으로 두고, DT `interrupts = <17 4>`(LEVEL_HIGH)와 `IRQF_TRIGGER_HIGH`로 맞췄다. 래치는 IRQ 스레드가 INT_STATUS를 읽어야 풀리므로 처리 전에 알림이 사라지지 않는다. mainline은 반대로 DT 값을 읽어 칩을 맞춘다([09 문서](09-iio-direct.md#왜-mainline은-dt의-irq-종류로-칩-설정을-정하는가)).

### 왜 devm이 아니라 kref로 상태를 관리하는가
앱이 `/dev/mpu6050`을 연 채로 overlay를 제거하면 remove 이후에도 fd가 남는다. devm으로 할당하면 remove와 함께 메모리가 사라져 남은 fd가 해제된 메모리를 가리킨다. 그래서 probe가 참조 1개, open이 참조 1개를 잡고 마지막 `kref_put`에서 해제한다([kref_init L539](../../examples/mpu6050/mpu6050_drv.c#L539), [mpu6050_free L281](../../examples/mpu6050/mpu6050_drv.c#L281)).

### 왜 misc 장치로 만들었고, 다음은 IIO인가
misc는 major 10을 공유하는 문자 디바이스라서 `register_chrdev`·`mknod` 없이 `/dev/mpu6050`이 자동으로 생긴다. 대신 데이터 형식, 큐, 대기, 단위 변환을 모두 직접 약속해야 했다. 센서와 상관없는 이 부분을 표준으로 제공하는 것이 IIO이고, 무엇이 대체되는지는 [09 문서의 비교표](09-iio-direct.md#왜-iio인가)에 있다.

## 4. 구현 흐름

### 4-1. probe: 센서 설정 → IRQ → 노드 공개
순서가 중요하다. **IRQ를 받을 준비가 끝난 뒤 센서 알림을 켜고, 모든 준비가 끝난 뒤 노드를 공개한다.**

| 순서 | 하는 일 | 코드 |
| --- | --- | --- |
| 1 | DT IRQ 존재·I2C 기능 확인, WHO_AM_I = 0x68 확인 | [L492](../../examples/mpu6050/mpu6050_drv.c#L492) |
| 2 | 리셋 → 클럭·범위·100Hz·INT 조건 설정, 쓴 값을 다시 읽어 확인 | [init_sensor L98](../../examples/mpu6050/mpu6050_drv.c#L98), [write_verify L75](../../examples/mpu6050/mpu6050_drv.c#L75) |
| 3 | FIFO 정지 → 리셋 → 6축 적재 시작 | [reset_fifo L151](../../examples/mpu6050/mpu6050_drv.c#L151) |
| 4 | state 할당, mutex·wait queue·kref 초기화 | [L539](../../examples/mpu6050/mpu6050_drv.c#L539) |
| 5 | threaded IRQ 등록 → INT_ENABLE=0x11로 센서 알림 켜기 | [L552](../../examples/mpu6050/mpu6050_drv.c#L552) |
| 6 | `misc_register` → `/dev/mpu6050` 생성 | [L566](../../examples/mpu6050/mpu6050_drv.c#L566) |

실패하면 `err_irq → err_put → err_sleep` 순서로 거꾸로 정리한다. probe가 실패하면 remove가 호출되지 않기 때문이다.

설정한 레지스터는 다음과 같다(근거: 제조사 Register Map).

| 레지스터 | 값 | 의미 |
| --- | --- | --- |
| PWR_MGMT_1 0x6b | 0x80 → 0x01 | 리셋 후 슬립 해제, X축 자이로 PLL 클럭 |
| GYRO_CONFIG 0x1b / ACCEL_CONFIG 0x1c | 0x00 / 0x00 | ±250 deg/s, ±2 g |
| CONFIG 0x1a / SMPLRT_DIV 0x19 | 0x03 / 9 | DLPF(대역폭 약 44Hz), 1kHz / (1+9) = 100Hz |
| INT_PIN_CFG 0x37 | 0x20 | active-high, 래치, INT_STATUS 읽기로 해제 |
| INT_ENABLE 0x38 | 0x11 | Data Ready + FIFO overflow |
| USER_CTRL 0x6a / FIFO_EN 0x23 | 0x40 / 0x78 | FIFO 동작, 가속도·자이로 6축 적재(온도 제외) |

### 4-2. IRQ: 래치 해제 → FIFO drain
IRQ 스레드는 INT_STATUS를 읽어 래치를 풀고, Data Ready면 drain을 호출한다([irq_thread L414](../../examples/mpu6050/mpu6050_drv.c#L414)).

```c
packets = fifo_count / MPU6050_PACKET_BYTES;      /* 완전한 12B 패킷만 */
remaining = packets * MPU6050_PACKET_BYTES;
while (remaining) {
	chunk = min(remaining, MPU6050_FIFO_CHUNK);   /* 24B = 2패킷 */
	ret = i2c_smbus_read_i2c_block_data(client, MPU6050_REG_FIFO_R_W,
					   chunk, data);
	...
	for (i = 0; i < chunk; i += MPU6050_PACKET_BYTES)
		mpu6050_queue_packet(state, &data[i]);
	remaining -= chunk;
}
```

- FIFO_COUNT로 쌓인 바이트를 보고 **완전한 패킷만** 읽는다. 남은 조각은 다음 IRQ에서 읽는다([L225](../../examples/mpu6050/mpu6050_drv.c#L225)).
- SMBus block read는 최대 32바이트라서 패킷 경계를 지키는 24바이트씩 읽는다.
- `FIFO_R_W`(0x74)는 같은 주소를 반복해서 읽는다. 센서가 내부에서 다음 바이트로 넘겨 준다.
- 넘치기 직전(988바이트 이상)이거나 전송 중 overflow가 생기면 `-EOVERFLOW`로 recover에 간다. 아직 전달하지 않은 큐를 비우고 FIFO를 한 번 리셋한다. 리셋까지 실패하면 IRQ를 끄고 지속 오류로 남긴다.

### 4-3. 커널 큐: 128개 링 버퍼
`head`는 다음에 읽을 위치, `queued`는 남은 개수다. 새 샘플은 `(head + queued) % 128`에 넣는다([queue_packet L193](../../examples/mpu6050/mpu6050_drv.c#L193)). 큐가 차면 가장 오래된 하나를 버리고 `error = -EOVERFLOW`를 남긴다. 앱이 열려 있지 않으면 순번만 올리고 저장하지 않는다.

센서 패킷(12B)과 앱이 받는 구조체(16B)는 다르다. 드라이버가 big-endian 6축을 정수로 바꾸고 4바이트 순번을 붙인다([mpu6050_data.h](../../examples/mpu6050/mpu6050_data.h)).

### 4-4. read: 잠금을 풀고 잔다
read는 mutex 안에서 **제거 → 지속 오류 → 일회성 오류 → 데이터** 순으로 확인하고, 데이터가 없으면 잠금을 풀고 잔다([read L327](../../examples/mpu6050/mpu6050_drv.c#L327)).

```c
mutex_unlock(&state->lock);
/* 상태 mutex를 놓고 자야 IRQ 스레드가 새 샘플을 저장할 수 있다. */
ret = wait_event_interruptible(state->wait,
	!READ_ONCE(state->client) ||
	READ_ONCE(state->fatal_error) || READ_ONCE(state->error) ||
	READ_ONCE(state->queued));
```

잠금을 잡은 채 자면 IRQ 스레드가 큐에 넣지 못해 서로 기다리게 된다. 깨어나면 다시 잠그고 조건을 처음부터 본다. `copy_to_user`가 성공한 뒤에만 `head`를 옮기므로, 복사가 실패해도 샘플은 남는다.

### 4-5. remove: 막고 → 깨우고 → 기다리고 → 놓는다
[remove L589](../../examples/mpu6050/mpu6050_drv.c#L589)의 순서다.

1. `misc_deregister`: 새 open을 막고 노드를 지운다.
2. `stop_irq`: 센서 알림을 끄고 `client = NULL`로 바꾼 뒤 잠든 read를 깨운다(→ `-ENODEV`).
3. `free_irq`: 진행 중인 IRQ 스레드가 끝날 때까지 기다린다. 스레드도 같은 mutex를 쓰므로 **잠금을 푼 뒤** 호출한다([L489](../../examples/mpu6050/mpu6050_drv.c#L489)).
4. FIFO를 끄고 슬립, 통계를 출력하고 `kref_put`한다. 열린 fd가 있으면 마지막 release에서 해제한다.

## 6. 트러블슈팅과 한계

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| 빠르게 돌릴 때 gyro Y가 `-250.137` | raw가 −32768(s16 하한)이고 −32768/131 = −250.137. ±250 deg/s 범위 포화 | 변환 오류가 아니다. 빠른 회전이 대상이면 FS_SEL과 앱의 `GYRO_LSB_PER_DPS`([L13](../../examples/mpu6050/mpu6050_app.c#L13))를 함께 바꾼다 |

**현재 버전 검증 (2026-11-06)**

| 항목 | 결과 |
| --- | --- |
| probe·노드 | FIFO 설정·single-reader 로그, `/dev/mpu6050`, driver 링크 확인 |
| 수집 | 흔드는 동안 20개 수신, Seq 6966~6985, Skip 전부 0, discontinuities 0, 종료 0 |
| 해제 | overlay 제거 후 IRQ 행·노드 없음, rmmod 후 lsmod 없음 |
| REMOVE 통계 | samples 10913, max-batch 1, overflows / resets / queue-overruns 0 |

- 미검증: IRQ 한 번에 여러 패킷 drain(max-batch가 1이었음), 큐 넘침·FIFO 복구 경로, 두 번째 open의 EBUSY, read 대기 중 장치 제거.
- 한계: 샘플별 시각이 없어 카메라와 시간 정렬을 할 수 없다. Seq는 드라이버가 붙인 순번이라 센서 FIFO에서 잃은 개수는 알 수 없다.

**더 보기**
- 리셋 비트에는 왜 `write_verify`를 쓰지 않는가 → 쓰고 나면 0으로 자동 해제되기 때문 ([reset_fifo L151](../../examples/mpu6050/mpu6050_drv.c#L151))

- mainline `inv_mpu6050`은 FIFO와 시각을 어떻게 다루는가 → [09 문서 2-2](09-iio-direct.md#2-2-mainline-inv_mpu6050와의-차이)
