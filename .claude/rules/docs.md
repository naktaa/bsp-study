# 문서 작성 규칙

AGENTS.md에서 옮긴 기존 문서 기준에 하네스 운영 규칙을 추가했다. 문서는 Claude Code가 작성·갱신한다.

## 하네스 문서 (추가)
- `docs/tasks/T-NNN-<주제>.md`: TASK 하나당 파일 하나. 병렬 트랙 TASK는 `T-Bxx-<주제>.md`(부팅)·`T-Sxx-<주제>.md`(센서)로 짓는다(AGENTS.md 병렬 트랙). `docs/tasks/_template.md` 형식을 따르고 섹션별 작성자를 지킨다. 섹션 제목의 작성자 표시(`(Claude)`·`(Codex)`)는 유지하되, 역할 분담을 바꾼 경우에도 "역할 예외" 같은 문구는 쓰지 않는다. 완료된 TASK 파일은 삭제하지 않는다.
- `docs/interview/<주제>.md`: 단계별 면접용 1페이지 요약. 구성은 **한 줄 요약 → 구조 그림/흐름 → 핵심 API와 선택 이유 → 실측값 → 트러블슈팅 1~2개 → 예상 질문과 답**. 간결체(~함·~음·제외), 두괄식으로 쓰고 과장하지 않는다. 날짜·TASK 번호·환경을 괄호로 나열하지 않고, 한 줄 요약 아래 '관련 파일'에 TASK·학습 문서·소스 링크를 모은다(Git 대상이 아닌 `external/` 경로는 텍스트로 적는다). 완료한 것과 설계·계획만 한 것을 구분한다.
- 학습 문서의 분량은 제한하지 않는다. 대신 단계별 검증 로그·중복 설명·다른 문서에 있는 정보(커밋 등)는 넣지 않는다. 면접 복습용 내용은 학습 문서가 아니라 interview 문서에 둔다.
- 사용자가 직접 수정한 문장은 사실 오류가 아니면 유지한다. 오류로 보이면 바꾸기 전에 근거와 함께 알린다.
- 실습 학습 문서의 기본 구조는 **개요 → 왜 이 방식인가·구현 구조(그림 포함) → 준비 → 단계별 재현[목적·명령·줄 링크·확인 포인트·설명] → 트러블슈팅 → 미검증**이다.
- 구현 설명은 데이터가 흐르는 순서를 따라 "무슨 일이 일어나고 → 드라이버가 무엇을 하고 → 왜 그런가" 위주의 학습 자료로 쓴다. 모든 함수·인자를 설명하지 않고 세부는 줄 링크로 넘기며, 코드는 이해에 꼭 필요한 부분만 짧게 발췌한다.
- 구조·데이터 흐름은 Mermaid를 쓰지 않고 일반 마크다운으로 바로 보이게 넣는다. 파이프라인은 `A → B → C` 한 줄(경로가 여럿이면 목록 한 항목에 한 줄), 아키텍처·계층은 `계층 | 구성 요소 | 하는 일` 표로 쓴다. 장치·DT·드라이버·프레임워크 사이 연결처럼 상자와 연결이 여럿인 구조는 흐름 줄·표에 더해 `text` 코드 블록의 ASCII 블록도(`+---+` 상자, `|`·`-->`·`v` 연결)로 시각 자료를 보충한다. 상자 안 라벨은 영어·코드 이름만 써서 정렬을 유지하고(한글은 폭이 달라 테두리가 어긋남), 한글 설명은 그림 아래 표·목록에 둔다. SVG·draw.io 등 이미지 파일은 만들지 않는다.
- 줄 링크는 시작 줄만 건다(`[mpu6050_iio.c#L161](mpu6050_iio.c#L161)`). 코드 변경으로 줄 번호가 바뀌면 /close-task에서 해당 문서의 줄 링크를 함께 갱신한다.

## 기존 문서 기준
- README: 프로젝트 개요·실습 문서 링크. docs/bringup.md: 현재 환경·장비·배선·타깃 정보와 기존/현재 커널 구분. docs/roadmap.md: 학습 순서·완료 기준.
- 실습 학습 파일은 `cross-compile.md`, `kernel-module.md`, `char-device.md`처럼 주제를 드러내는 짧은 이름으로 짓는다. README.md는 저장소 개요·문서 진입점에 사용하고, 문서 이름 변경 시 모든 링크를 함께 갱신한다.
- docs/worklog.md: 현재 상태·완료 결과·미해결 문제·다음 작업·상세 문서 링크만 간략히 유지한다. 명령·상세 설명을 중복하지 않는다.
- 실습 학습 문서는 실제 구현을 읽고 이해하는 학습 문서로 쓰며, 구성은 위 하네스 절의 기본 구조를 따른다. 커널 구축 등 절차 중심 문서는 해당 작업 흐름에 맞추되 개념·이유·재현 명령·검증 근거를 유지한다.
  - examples/hello/cross-compile.md: 기존 ARM64 사용자 프로그램 실습을 유지·보완한다.
  - docs/kernel-build.md: 소스 확보·커밋 고정·설정·크로스 빌드·백업·배포·initramfs·부팅 설정·동작 확인·복구를 정리한다.
  - examples/hello_module/kernel-module.md: 모듈 코드·Makefile의 핵심과 크로스 빌드·전송·로드·해제·로그 확인을 정리한다.
  - examples/char_device/char-device.md: 문자 디바이스의 현재 구현·호출 흐름·코드 해설·사용자/커널 경계와 단계별 검증을 정리한다.
  - examples/mpu6050/mpu6050.md: MPU6050의 현재 I2C 구현·DT 매칭·레지스터 접근과 사용자 실측·재현 절차를 정리한다.
  - examples/mpu6050_iio/iio-direct.md: 기존 FIFO 예제를 보존하고 별도로 진행하는 IIO 채널·raw/scale·트리거 버퍼 실습의 코드와 검증을 정리한다.
  - examples/platform_device/platform-device.md: Device Tree·platform 장치·드라이버 매칭과 probe/remove, 현재 구현·검증 절차를 정리한다.
- 전체 흐름에서 누가·언제·어떤 함수를 호출하는지 먼저 연결한다. 실제 소스를 링크하고 이해에 필요한 코드만 의미 있는 블록으로 제시한 바로 아래에 해설한다. 주요 함수·구조체·인자·반환값·오류 처리와 작성 이유를 설명한다.
- 함수 포인터·static·const·주소 전달 등 필요한 C 문법은 해당 코드에 연결한다. 모듈 로드/장치 open, fd/struct file, 장치 등록/노드 생성, 등록 해제/노드 삭제처럼 혼동하기 쉬운 개념을 구분하고 사용자 질문을 관련 설명에 합친다.
- VEDA 비교는 실제 확인한 코드 차이와 변경 이유를 남긴다. 현재 구현과 미구현 기능을 구분하고 예상 동작·일반 주의사항을 실제 트러블슈팅으로 기록하지 않는다.
- 학습 문서는 현재 구현 중심으로 갱신한다. 단계별 학습 흐름은 개념의 순서로 유지하며 중간 코드·명령·상태 보고를 계속 누적하지 않는다. 과거 기록은 현재 이해에 필요한 차이와 검증 근거만 간략히 보존한다. 본문·코드 발췌·VEDA 비교는 현재 소스와 맞추고 반복 재현 명령은 하나의 절차로 통합하며, 미검증·출력 미수신 단서는 검증 현황에 모은다.
- 학습에 필요한 설명은 분량이나 줄 수를 줄이기 위해 생략하지 않는다. 반복 설명은 한곳에 모으고 필요한 곳에서 링크한다. 기존 실습 학습 문서를 보완하며 중복 문서를 만들지 않는다. 매 질문마다 고치기보다 의미 있는 구현 단계가 끝났을 때 갱신한다.
- 명령마다 WSL/Pi, 작업 디렉터리와 선행 조건을 명확히 한다. 변수는 같은 블록에서 정의하거나 초기화 위치를 명시해 새 터미널에서도 재현할 수 있게 한다.
- 실제 사용한 소스 커밋·커널 버전·설정·명령과 관측 결과를 기준으로 작성한다. 미확인 최종 config.txt 등은 추측하지 말고 확인 필요로 표시한다.
- BSP 이해·재현에 필요한 기술적 시행착오는 관련 학습 문서에 남긴다. 취소·요청 변경·문구 수정 등 행정적 이력은 제외한다.
- 과거 결과는 당시 관측으로 현재 환경·최신 코드의 결과와 구분한다. 중요한 검증 결과는 짧은 표·대표 로그로 보존하고 오래된 다음 작업·미검증 표시는 실제 진행 상태에 맞춰 갱신한다.
- 단계 완료는 보드 실측 등 완료 조건의 근거가 있을 때만 표시한다. 복구 절차 준비·실제 복구 성공 및 수정한 절차의 정적 검토·재실행 검증을 구분한다.
