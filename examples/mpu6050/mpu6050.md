## 구현 범위

소스는 [mpu6050_drv.c](mpu6050_drv.c), [mpu6050_data.h](mpu6050_data.h), [mpu6050_app.c](mpu6050_app.c), [mpu6050-overlay.dts](mpu6050-overlay.dts), [Makefile](Makefile)이다. 기존 커널의 I2C 컨트롤러 드라이버를 이용해 직접 작성한 센서 드라이버가 데이터를 수집한다.

현재 구현은 **DT 매칭·초기화 → Data Ready IRQ에서 샘플 읽기·최신 한 건 보관 → read 대기자 깨우기 → 사용자 공간 전달 → 해제**다. 앱은 별도 sleep 없이 blocking read를 20회 수행하고 g·deg/s 표와 Seq/Skip을 출력한다. 커널은 순번과 raw를 전달하고 단위 환산은 앱에서만 한다. 최신 한 건 보관이므로 FIFO처럼 모든 샘플을 보존하지 않는다. 센서 FIFO·IIO·정확한 주기 제어·각도/위치 추정·오프셋 보정은 아직 구현하지 않았다.

대상은 Pi 4, 커널 `6.18.59-v8-bsp-study01`, 소스 커밋 `b3495ea401d709af0701a85babcba5e3d788a602`이다. [커널 구축](../../docs/kernel-build.md)에서 준비한 WSL 빌드 디렉터리 `out/kernel-rpi4`를 그대로 사용한다. 실제 배선은 [bringup](../../docs/bringup.md#모듈과-핀-연결표)에서 관리한다.

## 전체 실행 흐름

1. insmod로 I2C 드라이버를 등록하고 overlay로 주소 0x68·GPIO17 IRQ를 선언한다. 커널이 probe를 호출한다.
2. 식별·리셋·측정 범위·DLPF·공칭100Hz·INT 조건을 설정한다. state의 mutex·wait queue·kref를 준비한 뒤 IRQ를 등록하고 센서 알림을 활성화한다. 마지막으로 misc 장치를 공개한다.
3. 앱이 open하면 파일별 ctx를 만들고 현재 sequence를 seen_sequence로 저장한다. open 이전에 보관된 샘플을 즉시 주는 대신 open 이후의 새 결과를 기다린다.
4. 새 Data Ready가 발생하면 IRQ 스레드가 INT_STATUS를 읽어 래치를 해제하고 센서14바이트를 읽는다. raw를 해석해 최신 구조체에 저장하고 순번을 갱신한다.
5. IRQ 스레드가 wait queue의 대기자를 깨운다. 앱의 read는 파일별 마지막 순번과 다른 결과가 있으면 저장된 샘플을 로컬로 복사하고 copy_to_user로16바이트를 반환한다. read 자체는 I2C를 호출하지 않는다.
6. 앱은 g·deg/s로 환산해 Seq·Skip과 함께 출력하고 즉시 다음 read를 호출한다. 새 결과가 없으면 다시 잠든다. 기본20회 뒤 close한다.
7. overlay 제거 시 misc 등록 해제 → 센서 알림 차단·client=NULL → 대기자 깨우기 → free_irq로 IRQ 종료 대기 → 슬립 시도 순서로 처리한다. 대기하던 read는 -ENODEV를 반환한다. 열린 파일은 kref로 상태 수명을 유지하며 마지막 release에서 해제한다.
8. rmmod로 I2C 드라이버 등록을 해제한다. 같은 장치를 다시 생성해도 기존 열린 파일이 새 장치로 자동 연결되지는 않는다.

장치와 드라이버의 등록 순서는 반대여도 매칭될 수 있다. 여기서는 [platform 실습](../platform_device/platform-device.md)과 같이 드라이버를 먼저 등록한다.

## 코드 해설

### 1. 센서를 기존 I2C 버스에 선언

```dts
/dts-v1/;
/plugin/;

/ {
	compatible = "brcm,bcm2711";

	fragment@0 {
		target = <&gpio>;

		__overlay__ {
			mpu6050_int_pins: mpu6050-int-pins {
				pins-int {
					pins = "gpio17";
					function = "gpio_in";
					bias-pull-down;
				};
			};
		};
	};

	fragment@1 {
		target = <&i2c1>;

		__overlay__ {
			#address-cells = <1>;
			#size-cells = <0>;
			status = "okay";

			mpu6050@68 {
				compatible = "nakta,mpu6050-study";
				reg = <0x68>;
				status = "okay";
				pinctrl-names = "default";
				pinctrl-0 = <&mpu6050_int_pins>;
				interrupt-parent = <&gpio>;
				/* GPIO17, IRQ_TYPE_LEVEL_HIGH */
				interrupts = <17 4>;
			};
		};
	};
};
```

`&i2c1`은 기존 DT 심볼로, 이번 배선의 GPIO2/3을 사용하는 컨트롤러를 가리킨다. platform 예제는 루트에 장치를 추가했지만 이번 센서는 **I2C 컨트롤러의 자식**이다. 부모 버스가 자식 장치를 어떻게 해석할지 결정한다.

이 I2C 버스의 `reg`는 CPU 메모리 주소가 아니라 **7비트 I2C 주소**다. `#address-cells = <1>`은 주소를 한 셀로 표현하고 `#size-cells = <0>`은 MMIO 영역 크기를 붙이지 않는다는 뜻이다. 노드의 `@68`과 `reg`를 맞춘다. DT 선언만으로 센서의 AD0 전압이나 실제 주소가 바뀌지는 않는다.

`pinctrl-0`은 GPIO17을 gpio_in·풀다운으로 설정하는 핀 그룹을 참조한다. 현재 BCM2711 드라이버가 지원하는 generic pinctrl 표기를 사용했다. `interrupt-parent = <&gpio>`와 `interrupts = <17 4>`는 GPIO 컨트롤러의 line 17, HIGH 레벨 IRQ를 뜻한다. 숫자 4는 IRQ_TYPE_LEVEL_HIGH이고 물리 핀 번호는 11이다. 현재 dtc 규칙은 C 전처리를 하지 않으므로 DT에 숫자를 쓰고 의미를 주석으로 남겼다. 최종 Linux IRQ 번호는 커널이 매핑해 client->irq로 전달하며 17로 하드코딩하지 않는다.

`nakta,mpu6050-study`는 학습 드라이버를 선택하기 위한 로컬 compatible이다. 공식 MPU6050 binding이나 제품용 식별자가 아니다. 기존 드라이버용 `invensense,mpu6050`을 함께 적지 않는다. 이후 기존 IIO 드라이버로 전환할 때는 이 overlay와 학습 드라이버를 해제하고 해당 binding에 맞춘다.

### 2. 필요한 전송 기능 확인

```c
if (!i2c_check_functionality(client->adapter,
			     I2C_FUNC_SMBUS_BYTE_DATA |
			     I2C_FUNC_SMBUS_READ_I2C_BLOCK))
	return dev_err_probe(&client->dev, -EOPNOTSUPP,
			     "[PROBE] required I2C transfers unsupported\n");
```

`client`는 커널이 전달하는 현재 센서 장치의 포인터다. `client->adapter`는 이 센서가 연결된 버스이고, `client->addr`에는 DT에서 읽은 주소가 있다. 사용자 코드처럼 `/dev/i2c-1`을 open하거나 주소를 다시 지정할 필요가 없다.

`I2C_FUNC_SMBUS_BYTE_DATA`는 byte-data 읽기와 쓰기 기능을 함께 요구한다. 식별 전용 버전은 읽기만 요구했지만 현재는 설정 레지스터에 데이터를 쓰므로 쓰기 지원도 확인한다. 추가한 `I2C_FUNC_SMBUS_READ_I2C_BLOCK`은 측정 구간을 한 전송에서 연속으로 읽을 수 있는지 확인한다. `|`는 필요한 기능 비트를 합치는 비트 OR이며, 둘 중 하나만 지원해도 된다는 논리 OR가 아니다. 컨트롤러가 SMBus 전용 하드웨어일 필요는 없다. I2C 코어가 지원되는 일반 I2C 전송으로 해당 동작을 구현할 수도 있다. 지원 여부를 확인한 뒤 API를 쓴다.

`dev_err_probe()`는 장치 정보와 오류 메시지를 출력하고 전달한 오류 코드를 반환한다. `&client->dev`는 구조체 안의 `struct device` 멤버 주소다. 여기서는 지원하지 않는 전송 방식에 `-EOPNOTSUPP`를 반환한다.

### 3. WHO_AM_I 읽기와 반환값 검사

```c
static int mpu6050_probe(struct i2c_client *client)
{
	struct mpu6050_state *state;
	int ret;

	if (client->irq <= 0)
		return dev_err_probe(&client->dev, -EINVAL,
				     "[IRQ] missing Device Tree interrupt\n");

	if (!i2c_check_functionality(client->adapter,
				     I2C_FUNC_SMBUS_BYTE_DATA |
				     I2C_FUNC_SMBUS_READ_I2C_BLOCK))
		return dev_err_probe(&client->dev, -EOPNOTSUPP,
				     "[PROBE] required I2C transfers unsupported\n");

	ret = i2c_smbus_read_byte_data(client, MPU6050_REG_WHO_AM_I);
	if (ret < 0)
		return dev_err_probe(&client->dev, ret,
				     "[PROBE] failed to read WHO_AM_I\n");

	if (ret != MPU6050_WHO_AM_I)
		return dev_err_probe(&client->dev, -ENODEV,
				     "[PROBE] unexpected WHO_AM_I=0x%02x\n",
				     ret);

	dev_info(&client->dev, "[PROBE] addr=0x%02x, WHO_AM_I=0x%02x\n",
		 client->addr, ret);

	ret = mpu6050_init_sensor(client);
	if (ret)
		goto err_sleep;

	state = kzalloc(sizeof(*state), GFP_KERNEL);
	if (!state) {
		ret = -ENOMEM;
		goto err_sleep;
	}

	state->client = client;
	mutex_init(&state->lock);
	init_waitqueue_head(&state->wait);
	kref_init(&state->ref);
	state->misc.minor = MISC_DYNAMIC_MINOR;
	state->misc.name = "mpu6050";
	state->misc.fops = &mpu6050_fops;
	state->misc.parent = &client->dev;
	state->misc.mode = 0600;

	ret = i2c_smbus_read_byte_data(client, MPU6050_REG_INT_STATUS);
	if (ret < 0) {
		dev_err_probe(&client->dev, ret, "[IRQ] failed to clear pending status\n");
		goto err_put;
	}

	ret = request_threaded_irq(client->irq, NULL, mpu6050_irq_thread,
				   IRQF_TRIGGER_HIGH | IRQF_ONESHOT,
				   "mpu6050-data-ready", state);
	if (ret) {
		dev_err_probe(&client->dev, ret, "[IRQ] registration failed\n");
		goto err_put;
	}

	/* Linux의 수신 준비가 끝난 뒤 센서의 알림을 활성화한다. */
	ret = mpu6050_write_verify(client, MPU6050_REG_INT_ENABLE, MPU6050_DATA_READY);
	if (ret)
		goto err_irq;

	/* 모든 상태를 준비한 뒤 사용자에게 장치 노드를 공개한다. */
	ret = misc_register(&state->misc);
	if (ret) {
		dev_err_probe(&client->dev, ret, "[CHAR] registration failed\n");
		goto err_irq;
	}

	i2c_set_clientdata(client, state);
	dev_info(&client->dev, "[IRQ] irq=%d, data-ready nominal=100 Hz\n", client->irq);
	dev_info(&client->dev, "[CHAR] /dev/mpu6050 ready: IRQ latest-sample read\n");

	return 0;

err_irq:
	mpu6050_stop_irq(state);
err_put:
	kref_put(&state->ref, mpu6050_free);
err_sleep:
	/* 초기화·등록 실패 원인은 유지하고 슬립 전환은 별도로 시도한다. */
	mpu6050_sleep(client);
	return ret;
}
```

`MPU6050_REG_WHO_AM_I`는 `0x75`, `MPU6050_WHO_AM_I`는 예상 내용인 `0x68`이다. 앞서 실행한 `i2ctransfer -y 1 w1@0x68 0x75 r1`과 같은 레지스터 읽기 목적을 커널 API로 수행한다. 이 호출 자체는 식별 읽기다. 그다음 초기화 함수에서 센서 설정을 변경한다.

이 API는 성공 시 **0~255의 데이터**, 실패 시 음수 오류를 반환한다. 따라서 `ret`는 `int`로 받고 음수부터 검사한다. 처음부터 `u8`로 받으면 음수 오류가 잘려 데이터처럼 보일 수 있다. 정상 통신했어도 식별값이 다르면 `-ENODEV`로 probe를 실패시킨다. 이 단계에서는 예상 식별값 확인까지만 하며 같은 값을 쓰는 모든 칩을 엄밀히 구분하는 구현은 아니다.

`%02x`는 16진수를 최소 두 자리로 출력한다. probe의 최종 `return 0`은 읽은 데이터가 아니라 **드라이버 초기 연결 성공**을 뜻한다.

### 4. 센서 초기화와 설정 재확인

현재 설정은 다음과 같다. 전체 레지스터에 값을 쓰므로 표에 적힌 기능 외의 관련 비트도 그 값으로 정해진다. 다음 기능을 추가할 때 이 값을 함께 검토한다.

| 순서 | 레지스터 | 쓰는 값 | 의미 |
| --- | --- | --- | --- |
| 1 | PWR_MGMT_1 / 0x6b | 0x80 | DEVICE_RESET=1로 이전 설정 초기화. 100ms 대기 |
| 2 | PWR_MGMT_1 / 0x6b | 0x01 | SLEEP=0, CYCLE=0, TEMP_DIS=0, CLKSEL=1(X축 자이로 기준 PLL). 읽어서 확인 후 100ms 대기 |
| 3 | PWR_MGMT_2 / 0x6c | 0x00 | 가속도·자이로 모든 축의 standby 해제. 저전력 기동 주기 비트도 0 |
| 4 | GYRO_CONFIG / 0x1b | 0x00 | self-test 비활성화, FS_SEL=0 → ±250°/s |
| 5 | ACCEL_CONFIG / 0x1c | 0x00 | self-test 비활성화, AFS_SEL=0 → ±2g, 저역통과가 아닌 고역통과 필터 선택 비트도 0 |

설정 근거는 제조사 Register Map §4.4·4.5·4.28·4.29다. ±250°/s와 ±2g는 작은 움직임과 정지 상태를 처음 확인하기 위한 선택이다. raw 값은 사용자 앱에서 해당 범위의 감도로 나눈다. 아래 사용자 앱 해설에 변환식과 범위 의존성을 정리했다. Data Ready 준비를 위해 현재는 CONFIG=0x03, SMPLRT_DIV=9, INT_PIN_CFG=0x20도 초기화한다. 다음 IRQ 절에서 주기와 INT 조건을 설명한다. 측정 범위는 기존 ±2g·±250°/s로 유지한다.

```c
ret = i2c_smbus_write_byte_data(client, MPU6050_REG_PWR_MGMT_1,
			       MPU6050_RESET);
if (ret < 0)
	return dev_err_probe(&client->dev, ret,
			     "[INIT] failed to reset sensor\n");

msleep(MPU6050_STARTUP_MS);
```

식별 후 리셋해 반복 실행 시 이전 설정이 남는 영향을 줄인다. 리셋 비트는 자동으로 0이 되므로 이 쓰기에 일반적인 “쓴 값과 같은지” 비교를 적용하지 않는다. 리셋 쓰기 성공 뒤 기다리고 다음 설정을 진행한다. 타깃 커널의 `inv_mpu_core.c`도 식별 후 리셋과 100ms 대기를 수행한다.

`MPU6050_STARTUP_MS`는 100이다. 같은 커널의 power-up 100ms·gyro startup 60ms 정의를 참고해 슬립 해제 후에도 100ms를 기다리는 단순한 학습용 정책을 선택했다. 모든 상태 변화의 데이터시트 최소 시간이 정확히 100ms라는 뜻은 아니다. `msleep()`은 현재 작업을 재우므로 CPU를 바쁜 대기로 점유하지 않는다. probe는 잠들 수 있는 문맥이므로 사용 가능하다.

이후 초기화 함수는 `mpu6050_write_verify()`를 차례로 호출한다.

```c
ret = mpu6050_write_verify(client, MPU6050_REG_PWR_MGMT_1,
			   MPU6050_CLK_PLL_XGYRO);
if (ret)
	return ret;

msleep(MPU6050_STARTUP_MS);

ret = mpu6050_write_verify(client, MPU6050_REG_PWR_MGMT_2, 0x00);
if (ret)
	return ret;

ret = mpu6050_write_verify(client, MPU6050_REG_GYRO_CONFIG,
			   MPU6050_GYRO_FS_250);
if (ret)
	return ret;

ret = mpu6050_write_verify(client, MPU6050_REG_ACCEL_CONFIG,
			   MPU6050_ACCEL_FS_2G);
if (ret)
	return ret;
```

각 호출은 **레지스터 주소와 설정값**을 넘긴다. `MPU6050_CLK_PLL_XGYRO`는 0x01, 두 측정 범위 상수는 모두 0x00이다. 값이 같아도 레지스터가 다르면 의미가 다르므로 이름을 나눴다. 이 함수들의 성공 반환은 0이고 실패는 음수이므로 `if (ret)`로 다음 설정을 중단한다.

```c
ret = i2c_smbus_write_byte_data(client, reg, value);
if (ret < 0)
	return dev_err_probe(&client->dev, ret,
			     "[INIT] failed to write reg=0x%02x\n", reg);

ret = i2c_smbus_read_byte_data(client, reg);
if (ret < 0)
	return dev_err_probe(&client->dev, ret,
			     "[INIT] failed to read reg=0x%02x\n", reg);

if (ret != value)
	return dev_err_probe(&client->dev, -EIO,
			     "[INIT] reg=0x%02x expected=0x%02x, got=0x%02x\n",
			     reg, value, ret);
```

공통 함수 `mpu6050_write_verify(client, u8 reg, u8 value)`의 핵심이다. `u8`은 8비트 레지스터 번호·데이터를 표현한다. 쓰기 API는 0/음수, 읽기 API는 0~255/음수라는 반환 규칙 차이가 있다. 읽은 값은 오류를 보존하도록 `int ret`로 받는다. 통신은 성공했지만 내용이 다르면 `-EIO`다. 현재 선택한 안정적인 설정 레지스터에만 적용하며, 자동으로 바뀌는 비트나 읽기 부작용이 있는 레지스터에 이 함수를 그대로 쓰면 안 된다.

설정값 readback은 “레지스터 내용이 맞다”는 확인이다. PLL lock·측정 정확도·실제 샘플 출력을 직접 확인하는 검증은 아니다. 모든 설정을 확인한 경우에만 `[INIT] ready: ...`를 출력한다.

### 5. Data Ready 설정과 IRQ 스레드

현재 단계는 앞서 확인한 IRQ 알림을 **샘플 읽기·저장·사용자 read 깨우기**에 연결한다. 센서 FIFO나 소프트웨어 큐는 아직 추가하지 않는다.

| 설정 | 값 | 역할 |
| --- | --- | --- |
| CONFIG / 0x1a | 0x03 | DLPF_CFG=3, gyro 기준 출력률 1kHz. 이 설정의 대역폭은 가속도 44Hz·자이로 42Hz |
| SMPLRT_DIV / 0x19 | 9 | 1000 / (1+9) = 공칭 100Hz, 10ms마다 새 데이터 |
| INT_PIN_CFG / 0x37 | 0x20 | active HIGH·push-pull·래치 유지·INT_STATUS 읽기로만 해제 |
| INT_ENABLE / 0x38 | 0x01 | Data Ready 알림 활성화. IRQ 핸들러 등록 뒤 설정 |
| INT_STATUS / 0x3a | 읽기 | bit 0이 Data Ready 상태. 읽으면 상태·래치 해제 |

근거는 제조사 Register Map §4.2·4.3·4.14~4.16이다. 센서의 공칭 샘플 주기와 앱의 대기 시간은 다른 설정이다. Data Ready는10ms 간격을 목표로 발생하고 앱에는 별도100ms sleep이 없다. 앱은 새 수집 결과를 기다리는 blocking read를 사용한다. 100Hz를 설정했다고 실제 IRQ 처리율·앱 도착 간격·모든 샘플 보존을 보장한 것은 아니다. DLPF는 측정 신호를 저역통과시키므로 이전 기본 필터 상태와 지연·대역폭도 달라진다.

짧은 펄스 대신 IRQ 처리가 끝날 때까지 HIGH를 유지하는 latch 방식을 선택했다. INT_RD_CLEAR=0이므로 앱이 샘플 레지스터를 읽어도 알림이 지워지지 않고, IRQ 스레드가 INT_STATUS를 읽어 해제한다. DT와 request_threaded_irq의 트리거는 HIGH 레벨로 맞췄다. 센서 쪽 유지 조건과 Pi 쪽 트리거가 서로 맞아야 한다.

```c
ret = request_threaded_irq(client->irq, NULL, mpu6050_irq_thread,
			   IRQF_TRIGGER_HIGH | IRQF_ONESHOT,
			   "mpu6050-data-ready", state);
```

client->irq는 커널이 DT의 GPIO IRQ를 Linux IRQ 번호로 매핑한 결과다. 0 이하이면 이번 버전은 probe를 실패시킨다. 따라서 **이전 IRQ 없는 dtbo를 새 모듈과 섞지 않고 함께 빌드·전송**한다. request_threaded_irq는 성공 0, 실패 음수다. primary handler를 NULL로 두어 기본 primary가 스레드를 깨우게 하고, 실제 I2C 처리는 thread_fn에 맡긴다. 일반 hard IRQ 문맥에서 I2C나 mutex_lock처럼 잠들 수 있는 작업을 수행하지 않는다.

IRQF_ONESHOT은 스레드 처리 동안 해당 IRQ를 마스킹한다. “한 번만 발생”이 아니라 한 처리의 완료까지 재진입을 제어한다는 의미다. 상태 읽기로 HIGH를 해제한 뒤 IRQ를 다시 받을 수 있다. /proc/interrupts의 이름은 등록 인자인 mpu6050-data-ready다.

```c
static irqreturn_t mpu6050_irq_thread(int irq, void *data)
{
	struct mpu6050_state *state = data;
	struct mpu6050_sample sample;
	bool notify = false;
	u32 sequence;
	int status;
	int ret;

	mutex_lock(&state->lock);

	if (!state->client)
		goto out;

	status = i2c_smbus_read_byte_data(state->client, MPU6050_REG_INT_STATUS);
	if (status < 0) {
		ret = status;
	} else if (status & MPU6050_DATA_READY) {
		state->irq_count++;
		ret = mpu6050_read_sample(state->client, &sample);
	} else {
		goto out;
	}

	/* 최신 한 건만 보관하므로 느린 독자가 읽기 전 값은 덮어써진다. */
	sequence = state->sequence + 1;
	if (!ret) {
		sample.sequence = sequence;
		state->latest = sample;
	} else {
		dev_err_ratelimited(&state->client->dev,
				    "[IRQ] sample acquisition failed: %d\n", ret);
	}
	state->sample_error = ret;
	WRITE_ONCE(state->sequence, sequence);
	notify = true;

out:
	mutex_unlock(&state->lock);
	if (notify)
		wake_up_interruptible_all(&state->wait);
	return IRQ_HANDLED;
}
```

data는 IRQ 등록 시 넘긴 state 포인터다. status는 INT_STATUS의 데이터/음수 오류이고, ret는 샘플 읽기 성공0/음수 오류다. Data Ready 비트가 있으면 irq_count를 늘리고 mpu6050_read_sample을 호출한다. 성공하면 로컬 sample에 sequence를 붙여 latest에 복사한다. sample_error와 sequence를 게시한 뒤 mutex를 풀고 wake_up_interruptible_all로 모든 열린 파일의 대기자를 깨운다. IRQ_HANDLED는 IRQ 처리 결과이고 샘플 읽기 성공 자체를 의미하지 않는다.

sequence는 **소프트웨어가 게시한 수집 결과의32비트 순번**이다. 상태 읽기나 샘플 읽기 실패도 새 결과로 게시해 대기 앱이 오류를 받을 수 있게 한다. 실패 시 latest에 예전 값이 남아 있어도 sample_error를 먼저 검사하므로 예전 샘플을 정상 새 샘플로 전달하지 않는다. 더 최신 성공 결과가 먼저 덮어쓰면 중간 오류는 앱에 보이지 않을 수 있다. 하드웨어 내부의 모든 샘플 번호나 절대 시간은 아니다. unsigned32비트 순번은 끝에서0으로 돌아간다.

상태·샘플 데이터의 일관성은 mutex로 보호한다. wait 조건은 잠금 없이 검사하므로 sequence 갱신은 WRITE_ONCE, 조건 검사는 READ_ONCE를 사용한다. 이 매크로만으로 전체 샘플의 동기화가 해결되는 것은 아니며 실제 구조체 복사는 다시 mutex 안에서 수행한다. 상태 갱신 후 깨우고, 기다리는 쪽이 조건을 반복 검사하는 구조로 신호만 먼저 지나가는 문제를 피한다.

샘플마다 커널 로그를 찍지 않고 앱 표로 확인한다. 오류 로그는 dev_err_ratelimited로 제한한다. 상태 읽기가 실패하면 래치가 남을 수 있고, IRQ 처리 사이에 여러 샘플이 생성되면 상태 비트가 합쳐질 수 있다. IRQ 횟수나 sequence만으로 하드웨어 샘플 누락 전체를 판정할 수 없다.

```c
static void mpu6050_stop_irq(struct mpu6050_state *state)
{
	struct i2c_client *client;
	int ret;

	mutex_lock(&state->lock);

	client = state->client;
	ret = i2c_smbus_write_byte_data(client, MPU6050_REG_INT_ENABLE, 0x00);
	if (ret < 0)
		dev_warn(&client->dev, "[IRQ] failed to disable source: %d\n", ret);
	WRITE_ONCE(state->client, NULL);

	mutex_unlock(&state->lock);
	wake_up_interruptible_all(&state->wait);

	/* 핸들러도 같은 mutex를 쓰므로 잠금을 푼 뒤 핸들러 종료를 기다린다. */
	free_irq(client->irq, state);
}
```

정리에서는 mutex를 잡고 센서 INT_ENABLE=0을 쓰고 client를 NULL로 만든다. client 변경은 WRITE_ONCE로 게시한다. mutex를 푼 뒤 wait queue를 깨워 기존 read가 -ENODEV를 받을 수 있게 하고, free_irq로 진행 중인 핸들러의 종료를 기다린다. 잠금을 잡은 채 free_irq를 호출하면 같은 mutex를 기다리는 IRQ 스레드와 서로 기다릴 수 있다. free_irq가 완료되기 전에는 state 메모리를 해제하지 않는다.

이번에는 kref로 장치 상태 수명을 직접 관리하므로 request_threaded_irq/free_irq의 짝도 명시적으로 관리한다. devm IRQ를 등록해놓고 state만 먼저 해제하는 순서를 피한다. probe의 IRQ 등록 이후 실패는 err_irq → err_put → err_sleep 순서, IRQ 등록 이전 실패는 err_put 또는 err_sleep로 분기한다. 요청하지 않은 IRQ를 free하지 않는다.

### 6. 한 샘플 읽기와 바이트 해석

초기화 후 읽는 범위는 `ACCEL_XOUT_H(0x3b)`부터 `GYRO_ZOUT_L(0x48)`까지다.

| 버퍼 위치 | 레지스터 | 데이터 |
| --- | --- | --- |
| 0~1 | 0x3b~0x3c | 가속도 X, 상위 → 하위 바이트 |
| 2~3 | 0x3d~0x3e | 가속도 Y |
| 4~5 | 0x3f~0x40 | 가속도 Z |
| 6~7 | 0x41~0x42 | 온도, 이번에는 읽기만 하고 해석·출력하지 않음 |
| 8~9 | 0x43~0x44 | 자이로 X |
| 10~11 | 0x45~0x46 | 자이로 Y |
| 12~13 | 0x47~0x48 | 자이로 Z |

가속도 6 + 온도 2 + 자이로 6 = 14바이트다. 제조사 Register Map §4.17~4.19는 연속 읽기로 같은 샘플링 시점의 사용자용 측정 레지스터를 읽을 수 있다고 설명한다. 바이트나 축을 여러 전송으로 나누면 전송 사이에 새 샘플이 반영될 수 있다. 온도를 출력하지 않아도 중간 구간을 포함해 한 번에 읽는 이유다.

```c
static int mpu6050_read_sample(struct i2c_client *client,
			       struct mpu6050_sample *sample)
{
	u8 data[MPU6050_SAMPLE_BYTES];
	int ret;

	/* 같은 시점의 축 데이터를 얻도록 온도를 포함한 구간을 한 번에 읽는다. */
	ret = i2c_smbus_read_i2c_block_data(client, MPU6050_REG_ACCEL_XOUT_H,
					   sizeof(data), data);
	if (ret < 0)
		return ret;
	if (ret != MPU6050_SAMPLE_BYTES)
		return -EIO;

	sample->accel[0] = (s16)get_unaligned_be16(&data[0]);
	sample->accel[1] = (s16)get_unaligned_be16(&data[2]);
	sample->accel[2] = (s16)get_unaligned_be16(&data[4]);

	/* 바이트 6~7은 온도 값이며 이번에는 출력하지 않는다. */
	sample->gyro[0] = (s16)get_unaligned_be16(&data[8]);
	sample->gyro[1] = (s16)get_unaligned_be16(&data[10]);
	sample->gyro[2] = (s16)get_unaligned_be16(&data[12]);
	return 0;
}
```

`u8 data[14]`는 함수가 실행되는 동안만 사용하는 스택 버퍼다. `data`는 호출 시 첫 원소 주소로 전달되고, API는 읽은 바이트를 그 버퍼에 채운다. `sizeof(data)`는 이 함수 안에서 배열 전체 크기인 14다. 포인터 인자에 sizeof를 적용해도 배열 크기를 알 수 있다는 의미는 아니다. 이 helper의 로컬 버퍼 자체에는 별도 free가 필요하지 않다. 센서 접근과 최신 샘플 저장은 호출자인 IRQ 스레드가 장치 상태 mutex로 보호한다.

`i2c_smbus_read_i2c_block_data(client, 시작 주소, 길이, 버퍼)`는 성공 시 **읽은 바이트 수**, 실패 시 음수 오류를 반환한다. byte-data 읽기의 반환값이 데이터 자체였던 것과 구분한다. `ret < 0` 검사 후 14바이트인지 확인하고, 짧으면 `-EIO`를 반환한다. 일부만 받은 버퍼를 해석하거나 정상 샘플처럼 출력하지 않는다. 이 API의 최대 블록 길이는 32바이트이며 이번 요청은 그 안에 있다. helper는 성공 시 출력 인자 sample에 값을 채우고 0을 반환한다. runtime 읽기 오류는 음수로 호출자에게 전달하며 매 샘플을 커널 로그로 출력하지 않는다.

이것은 `i2c_smbus_read_block_data()`와 다른 **I2C block read**다. 일반 SMBus block read처럼 센서가 길이 바이트를 먼저 보내는 형식이 아니라, 호스트가 14바이트를 지정한다. 대상 커널의 `Documentation/i2c/smbus-protocol.rst`와 `i2c-core-smbus.c`에서 이 차이와 반환값을 확인했다. 바이트 읽기를 여러 번 반복하는 대체 경로는 사용하지 않는다.

`get_unaligned_be16(&data[0])`는 정렬을 가정하지 않고 상위 바이트가 먼저 오는 두 바이트를 CPU에서 사용할 16비트 숫자로 읽는다. `&data[0]`은 X축 데이터의 시작 주소이고, 다음 축은 두 칸씩 이동한다. 헤더는 현재 커널의 `<linux/unaligned.h>`를 사용한다. `(s16)`은 그 16비트 패턴을 부호 있는 값으로 해석한다. 예를 들어 바이트 `ff 00`은 unsigned로 65280이지만 s16으로 -256이다. 정렬·엔디언·부호 처리를 생략한 포인터 캐스팅으로 버퍼를 직접 읽지 않는다.

이 helper는 raw 여섯 축을 채운다. sequence는 호출자인 IRQ 스레드가 성공한 읽기 결과에 붙인다. 사용자 앱에서만 g·deg/s로 환산하며 각도나 위치로 변환하는 것은 아니다. 온도를 건너뛰므로 자이로는 data[6]이 아니라 **data[8]**에서 시작한다. 앱의 한 줄에 표시하는 가속도와 자이로는 같은 read 결과이며 각각 다시 센서에 접근하는 것이 아니다.

현재는 Data Ready IRQ가 샘플을 읽고 read는 최신 저장 결과를 가져간다. 타임스탬프와 실제 수집률 검증은 아직 다루지 않는다. 정지 상태라도 가속도에는 중력이 포함되고 자이로에는 오프셋·잡음이 있어 모든 축이 0이라고 기대하지 않는다.

### 7. 문자 인터페이스와 장치 상태 수명

#### 공유 데이터 구조체

```c
struct mpu6050_sample {
	__u32 sequence;
	__s16 accel[3];
	__s16 gyro[3];
};
```

[공유 헤더](mpu6050_data.h)를 커널과 앱이 함께 include한다. `__u32` 순번4바이트와 `__s16` 여섯 개12바이트로 현재 구조체는16바이트이며 각 배열은 X/Y/Z 순서다. 온도는 사용자에게 전달하지 않는다. 센서에서 읽는14바이트(온도 포함)와 앱에 주는16바이트(온도 제외·순번 포함)는 다르다. 이전12바이트 앱과 새 드라이버를 섞으면 count 검사에서 실패할 수 있으므로 모듈·앱을 함께 갱신한다. 드라이버가 센서의 big-endian 바이트를 정수로 바꾼 뒤 이 구조체에 채우며, 구조체 값은 타깃 CPU의 native endian이다. 네트워크 전송 형식이나 IIO ABI가 아닌 현재 앱과 드라이버 사이의 학습용 계약이다. 양쪽 헤더를 같이 갱신한다.

#### miscdevice를 선택한 이유

기존 문자 디바이스 실습은 register_chrdev와 수동 mknod로 major/minor 연결을 배웠다. 이번에는 센서 데이터 전달에 집중하기 위해 miscdevice를 선택했다. 이것도 **문자 디바이스**이며 file_operations와 copy_to_user를 그대로 쓴다. 기존 char_device 예제를 변경하거나 alloc_chrdev_region/cdev 학습을 완료한 것은 아니다.

probe에서 `misc.minor = MISC_DYNAMIC_MINOR`, `misc.name = "mpu6050"`, `misc.fops = &mpu6050_fops`, `misc.parent = &client->dev`, `misc.mode = 0600`을 설정한다. misc_register가 minor와 장치 모델 등록을 맡고, 현재 커널의 devtmpfs/udev 경로에서 /dev/mpu6050 노드가 만들어진다. mknod·노드 수동 삭제는 하지 않는다. misc는 major 10을 공유하며 minor는 동적이므로 고정하지 않는다. `/proc/misc`에서는 minor와 이름을 볼 수 있다. 권한은 root 읽기/쓰기 기준 0600이지만 드라이버가 제공하는 동작은 read뿐이다. 앱은 sudo로 실행한다.

노드 이름이 고정되어 이번 예제는 센서 한 개만 대상으로 한다. 같은 이름의 두 번째 장치를 동시에 등록하는 구성은 지원하지 않는다.

#### open과 release

```c
struct mpu6050_state {
	struct i2c_client *client;
	struct miscdevice misc;
	struct mutex lock;
	struct kref ref;
	unsigned long irq_count;
	wait_queue_head_t wait;
	struct mpu6050_sample latest;
	u32 sequence;
	int sample_error;
};

struct mpu6050_file {
	struct mpu6050_state *state;
	struct mutex read_lock;
	u32 seen_sequence;
};
```

state는 장치 전체의 최신 결과·wait queue·센서 연결을 관리한다. ctx는 열린 파일별 읽기 진행 상태다. 여러 파일이 같은 state를 보되 seen_sequence는 독립적이다. read_lock과 state->lock은 각각 같은 열린 파일의 동시 read와 장치 데이터 갱신을 보호하므로 역할이 다르다.

```c
static void mpu6050_free(struct kref *ref)
{
	struct mpu6050_state *state = container_of(ref, struct mpu6050_state, ref);

	kfree(state);
}

static int mpu6050_open(struct inode *inode, struct file *filp)
{
	struct miscdevice *misc = filp->private_data;
	struct mpu6050_state *state = container_of(misc, struct mpu6050_state, misc);
	struct mpu6050_file *ctx;

	ctx = kzalloc(sizeof(*ctx), GFP_KERNEL);
	if (!ctx)
		return -ENOMEM;

	/* misc 코어가 open과 deregister를 직렬화하는 동안 참조를 확보한다. */
	kref_get(&state->ref);
	ctx->state = state;
	mutex_init(&ctx->read_lock);

	mutex_lock(&state->lock);
	ctx->seen_sequence = state->sequence;
	mutex_unlock(&state->lock);

	filp->private_data = ctx;
	return nonseekable_open(inode, filp);
}

static int mpu6050_release(struct inode *inode, struct file *filp)
{
	struct mpu6050_file *ctx = filp->private_data;

	kref_put(&ctx->state->ref, mpu6050_free);
	kfree(ctx);
	return 0;
}
```

misc 코어는 사용자 open을 우리 open으로 넘기기 전에 filp->private_data에 struct miscdevice 주소를 넣는다. container_of는 이 멤버를 포함하는 바깥 struct mpu6050_state의 주소를 구한다. 파일별 struct mpu6050_file을 할당하고 ctx->state에 장치 상태를 저장한다. private_data는 ctx로 바꿔 이후 read/release에서 사용한다. ctx->seen_sequence는 open 시점의 순번이고 ctx->read_lock은 같은 열린 파일의 동시 read를 직렬화한다. 서로 다른 open은 각각 별도의 ctx를 갖는다. 파일별 문맥의 기본 개념은 [문자 디바이스 학습](../char_device/char-device.md)과 연결된다.

kref_init은 probe가 소유하는 참조 1개를 만든다. 성공한 open마다 kref_get으로 참조가 하나 늘고 마지막 release마다 하나 줄어든다. kref_put이0으로 만들면 mpu6050_free가 장치 상태를 해제한다. release는 파일별 ctx도 별도로 kfree한다. dup한 fd마다 open이 다시 호출되는 것은 아니며, 참조 기준은 열린 struct file이다. nonseekable_open은 현재 커널에서 항상 0을 반환하며 seek/pread/pwrite를 비활성화한다.

단순히 devm_kzalloc한 상태를 열린 파일에 보관하면 overlay 제거 시 메모리가 먼저 해제될 수 있다. 그래서 이 상태는 kzalloc+kref로 수명을 관리한다. 현재 커널 drivers/char/misc.c는 misc_open과 misc_deregister를 같은 misc_mtx로 직렬화한다. 그 보장 안에서 open이 참조를 확보하므로 등록 참조가 먼저 사라지는 경쟁을 피한다.

#### read와 반환 규칙

```c
static ssize_t mpu6050_read(struct file *filp, char __user *buf,
			    size_t count, loff_t *f_pos)
{
	struct mpu6050_file *ctx = filp->private_data;
	struct mpu6050_state *state = ctx->state;
	struct mpu6050_sample sample;
	int ret;

	if (!count)
		return 0;
	if (count < sizeof(sample))
		return -EINVAL;

	/* 같은 열린 파일의 동시 read가 같은 순번을 중복 전달하지 않게 한다. */
	ret = mutex_lock_interruptible(&ctx->read_lock);
	if (ret)
		return ret;

	for (;;) {
		ret = mutex_lock_interruptible(&state->lock);
		if (ret)
			goto out;

		if (!state->client) {
			mutex_unlock(&state->lock);
			ret = -ENODEV;
			goto out;
		}

		if (state->sequence != ctx->seen_sequence) {
			ret = state->sample_error;
			if (ret)
				ctx->seen_sequence = state->sequence;
			else
				sample = state->latest;
			mutex_unlock(&state->lock);
			break;
		}

		mutex_unlock(&state->lock);

		if (filp->f_flags & O_NONBLOCK) {
			ret = -EAGAIN;
			goto out;
		}

		/* 상태 mutex를 놓고 자야 IRQ 스레드가 새 샘플을 저장할 수 있다. */
		ret = wait_event_interruptible(state->wait,
			!READ_ONCE(state->client) ||
			READ_ONCE(state->sequence) != ctx->seen_sequence);
		if (ret)
			goto out;
	}

	if (ret)
		goto out;
	if (copy_to_user(buf, &sample, sizeof(sample))) {
		ret = -EFAULT;
		goto out;
	}

	ctx->seen_sequence = sample.sequence;
	ret = sizeof(sample);

out:
	mutex_unlock(&ctx->read_lock);
	return ret;
}

static const struct file_operations mpu6050_fops = {
	.owner = THIS_MODULE,
	.open = mpu6050_open,
	.release = mpu6050_release,
	.read = mpu6050_read,
};
```

count는 사용자 버퍼 크기이고 buf는 사용자 주소다. count=0은0,16 미만은-EINVAL이다.16 이상이면 최신 한 샘플16바이트만 반환하며 파일 오프셋을 진행시키거나 정상 EOF를 만들지 않는다. 바이너리 구조체이므로 cat으로 표시하지 않는다.

먼저 파일별 read_lock을 잡아 같은 열린 파일의 순번 검사·복사가 겹치지 않게 한다. state->lock 안에서 연결 상태와 순번을 확인하고, 새 결과가 있으면 오류 또는 최신 구조체를 가져온다. 새 결과가 없으면 **state->lock을 풀고** wait_event_interruptible로 잠든다. 센서 lock을 잡은 채 기다리면 IRQ가 값을 저장하지 못하므로 이 순서가 중요하다. 파일별 read_lock은 대기 동안 유지하되 IRQ 스레드는 그 lock을 사용하지 않는다.

wait 조건은 장치 제거 또는 새 sequence다. 깨운 뒤 for 루프가 다시 mutex를 잡고 조건을 확인하므로 깨어남 자체가 데이터 존재를 보장한다고 가정하지 않는다. O_NONBLOCK으로 열었고 새 데이터가 없으면 -EAGAIN이다. 현재 앱은 O_RDONLY이므로 blocking 동작한다. 시그널로 대기가 중단되면 커널의 음수 재시작 오류가 반환되고 syscall 계층에서 처리된다. INT가 들어오지 않으면 read는 기다리므로 연결·IRQ 확인이 선행 조건이며 Ctrl+C로 앱을 중단할 수 있다. 현재 poll/select 콜백·대기 타임아웃은 구현하지 않았다.

샘플을 로컬로 복사한 뒤 state lock을 풀고 copy_to_user한다. 사용자 복사 성공 후에만 ctx->seen_sequence를 그 샘플 순번으로 옮긴다. 복사 실패는-EFAULT이고 같은 순번을 읽었다고 처리하지 않는다. I2C 실패 결과를 반환할 때는 해당 결과 순번을 소비해 같은 오류만 반복 반환하지 않게 한다. 장치 제거는-ENODEV, 짧은 센서 읽기는-EIO다. 앱에서는 read=-1과 errno로 보인다.

최신 한 건은 여러 파일이 독립적으로 읽을 수 있다. 한 앱의 read가 다른 앱의 데이터를 소비하지는 않는다. 앱이 느리면 latest는 덮어써지고 sequence가 건너뛸 수 있다. 같은 열린 파일은 read_lock 때문에 같은 순번을 중복 전달하지 않는다. mutex 보호는 IRQ 게시·연결 해제·read 스냅샷의 경쟁을 막는 것이며 스케줄링 지연이나 샘플 보존을 보장하는 것은 아니다.

.owner = THIS_MODULE은 열린 파일이 사용하는 모듈 코드를 유지한다. 앱이 열려 있으면 일반 rmmod는 사용 중 오류가 날 수 있다. 이것만으로 DT 장치 unbind를 막거나 장치 상태 메모리까지 보존하는 것은 아니므로 mutex·client 차단·kref를 별도로 사용한다.


### 8. 매칭 테이블과 드라이버 등록

```c
static const struct of_device_id mpu6050_match[] = {
	{ .compatible = "nakta,mpu6050-study" },
	{},
};
MODULE_DEVICE_TABLE(of, mpu6050_match);

static const struct i2c_device_id mpu6050_ids[] = {
	{ "mpu6050-study", 0 },
	{},
};
MODULE_DEVICE_TABLE(i2c, mpu6050_ids);
```

OF 테이블은 DT compatible 매칭에 쓴다. I2C ID 테이블은 이름 기반 매칭과 I2C 모듈 별칭을 제공한다. 여기서는 DT를 사용하고 두 식별자 모두 실습 전용 이름으로 맞췄다. 두 테이블의 끝에는 종료 표시인 빈 항목이 있다. `static`은 이 소스 파일 안에서만 이름을 사용하게 하고 `const`는 테이블 내용을 수정하지 않도록 한다.

`MODULE_DEVICE_TABLE()`은 빌드 시 장치 별칭 정보를 모듈에 포함하게 한다. `modinfo -F alias`로 확인할 수 있다. 별칭이 있다고 전송한 파일이 자동으로 설치·로드되는 것은 아니다. 이번 실습에서는 `~/bsp/modules/`의 파일을 `insmod`로 직접 로드한다.

```c
static struct i2c_driver mpu6050_driver = {
	.probe = mpu6050_probe,
	.remove = mpu6050_remove,
	.id_table = mpu6050_ids,
	.driver = {
		.name = "mpu6050-study",
		.of_match_table = mpu6050_match,
	},
};
module_i2c_driver(mpu6050_driver);
```

`.probe = mpu6050_probe`는 함수를 지금 실행하는 표현이 아니라 콜백 주소를 등록하는 초기화다. 나중에 I2C 코어가 호출한다. 현재 6.18 소스의 선언에 맞춰 probe는 `int (struct i2c_client *)`, remove는 `void (struct i2c_client *)` 형식이다. 예전 자료의 probe 인자나 remove 반환형을 그대로 섞지 않는다.

`module_i2c_driver()`는 모듈 로드 시 드라이버 등록, 해제 시 등록 해제를 수행할 init/exit 경로를 만든다. 문자 디바이스의 `file_operations`를 등록하는 것과 다른 역할이다.

### 9. 해제와 자원

```c
static void mpu6050_remove(struct i2c_client *client)
{
	struct mpu6050_state *state = i2c_get_clientdata(client);

	/* 새 open을 막고 진행 중인 읽기가 끝난 뒤 센서 접근을 차단한다. */
	misc_deregister(&state->misc);
	mpu6050_stop_irq(state);
	mpu6050_sleep(client);

	dev_info(&client->dev, "[REMOVE] detached, data-ready count=%lu\n", state->irq_count);
	/* 열린 파일이 남아 있으면 마지막 release에서 메모리를 해제한다. */
	kref_put(&state->ref, mpu6050_free);
}
```

misc_deregister가 새 open을 막고 자동 생성 노드를 제거한다. stop_irq가 센서 알림을 끄고 client를 NULL로 게시한 뒤 대기 중인 read를 깨운다. 이후 IRQ 스레드 종료를 기다린다. 그 뒤 슬립을 시도하고 처리한 Data Ready 비트 횟수를 출력한다. 카운터는 free_irq 이후 읽으므로 IRQ 스레드의 갱신과 경합하지 않는다. 마지막 kref_put은 등록 참조를 반환하며 열린 파일이 남았다면 마지막 release에서 최종 free한다.

remove는 void이고 알림 비활성화·슬립 쓰기 실패는 경고로 보고한다. REMOVE 로그만으로 하드웨어 슬립 상태를 확인했다고 하지 않는다. 실패한 probe에는 remove가 호출된다고 기대하지 않으므로 probe 오류 라벨에서 단계별 자원을 정리한다. 원래 실패 코드는 유지하고 과거 설정 전체를 복원하는 rollback은 아니다.


### 10. Makefile

기존 [platform Makefile 해설](../platform_device/platform-device.md)의 Kbuild 분기·크로스 컴파일·호스트 dtc 사용 방식을 유지했다. `obj-m := mpu6050_drv.o`가 `.ko` 이름을 정하며, `all`은 `modules`, `overlay`, `app`을 만든다. 앱 규칙은 mpu6050_app.c와 공유 헤더를 의존성으로 두어 헤더 변경도 재빌드에 반영한다. APP_CC 기본값은 크로스 GCC이며 APP_CFLAGS는 -Wall -Wextra -O0 -g다. overlay 규칙은 DTS를 의존성으로 두고 `dtc -@`로 DT 심볼 참조에 필요한 정보를 포함한다.

`KDIR` 기본값은 현재 예제 디렉터리에서 `../../out/kernel-rpi4`를 절대 경로로 계산한다. `ARCH=arm64`, `CROSS_COMPILE=aarch64-linux-gnu-`, `LOCALVERSION=`를 전달해 같은 커널 빌드 결과를 참조한다. **dtc는 WSL에서 실행하는 호스트 프로그램**이며 ARM64 타깃 실행 파일이 아니다.

`make deploy`는 이미 만든 `.ko`·`.dtbo`·mpu6050_app을 각각 bsp/modules·bsp/overlays·bsp/apps로 전송만 한다. 자동 빌드·모듈 로드·overlay 적용은 하지 않는다. `clean`은 이 예제의 생성물을 지우며 커널 전체를 재빌드하지 않는다.

### 11. 사용자 앱의 읽기 함수와 반복 루프

```c
static int mpu6050_read_sample(int fd, struct mpu6050_sample *sample)
{
    ssize_t received;

    do {
        received = read(fd, sample, sizeof(*sample));
    } while (received == -1 && errno == EINTR);

    if (received == -1)
        return -1;
    if ((size_t)received != sizeof(*sample)) {
        errno = EIO;
        return -1;
    }

    return 0;
}
```

이 함수는 파일 디스크립터와 출력 구조체 포인터를 받는다. sizeof(*sample)은 포인터 크기가 아니라 가리키는 구조체 크기16이다. read가 시그널로 EINTR을 반환하면 재시도하고, 그 외 오류는 -1로 호출자에게 전달한다. 16바이트가 아닌 응답은 이 인터페이스 계약 위반으로 보고 errno=EIO를 설정한다. 성공이면 sample에 값이 채워지고 0을 반환한다. 커널 helper와 이름이 같지만 서로 다른 실행 공간·소스의 함수다.

main은 /dev/mpu6050을 O_RDONLY로 한 번 열고 읽기 함수를20번 호출한다. 이전 nanosleep·INTERVAL_MS를 제거했다. read가 새 결과를 기다리므로 앱에서 반복 확인하거나 고정 간격으로 재우지 않는다. 표에는 No.·Seq·Skip과 가속도/각속도를 출력한다. 읽기 실패면 close 후1,20회 완료면 close 후0이다. fflush(stdout)는 파이프에서도 출력을 바로 전달하기 위해 유지한다.

Seq는 드라이버의 게시 순번이며 앱 시작 시1일 필요가 없다. Skip은 이전에 받은 순번과의 차이에서1을 뺀 값이다. 첫 행은 비교할 이전 값이 없어0으로 표시한다. 32비트 unsigned 차이 계산이므로 정상적인 순번 wrap도 처리한다. Skip=0은 두 전달 사이 게시 결과가 연속이라는 뜻이며 하드웨어 데이터가 하나도 누락되지 않았다는 뜻은 아니다. 양수이면 최신 보관값이 앱 읽기 사이 덮어써졌거나 중간 오류 결과가 지나간 경우 등을 나타낸다.


#### 물리 단위 변환과 출력 형식

```c
/* 드라이버의 측정 범위 ±2g·±250°/s에 대응하는 감도다. */
#define ACCEL_LSB_PER_G 16384.0
#define GYRO_LSB_PER_DPS 131.0
```

현재 드라이버는 AFS_SEL=0(±2g), FS_SEL=0(±250°/s)으로 고정하므로 가속도 raw를 16384.0으로 나누면 g, 자이로 raw를 131.0으로 나누면 °/s다. 감도 근거는 [제조사 Product Specification §6.1·6.2](https://product.tdk.com/system/files/dam/doc/product/sensor/mortion-inertial/imu/data_sheet/mpu-6000-datasheet1.pdf)다. 이 상수는 앱이 센서 설정을 자동 조회한 결과가 아니므로 드라이버의 측정 범위를 바꾸면 앱의 감도·범위 안내도 함께 바꿔야 한다.

```c
        unsigned int skipped = i == 0 ? 0 : sample.sequence - previous_sequence - 1U;

        printf("%4d %10u %6u | %+8.3f %+8.3f %+8.3f | %+8.3f %+8.3f %+8.3f\n",
               i + 1, sample.sequence, skipped,
               sample.accel[0] / ACCEL_LSB_PER_G,
               sample.accel[1] / ACCEL_LSB_PER_G,
               sample.accel[2] / ACCEL_LSB_PER_G,
               sample.gyro[0] / GYRO_LSB_PER_DPS,
               sample.gyro[1] / GYRO_LSB_PER_DPS,
               sample.gyro[2] / GYRO_LSB_PER_DPS);
```

나누는 상수를 double로 작성해 정수 나눗셈으로 소수부가 잘리지 않게 한다. %+8.3f는 부호를 항상 표시하고 최소 폭 8칸·소수점 아래 3자리로 출력한다. 커널에서 부동소수점 연산을 하지 않고, 센서 raw 계약과 공유 구조체도 그대로 유지한다. 데이터 전송 경로는 같고 표현만 바뀌었다.

아래는 이전 raw 값과 임의의 순번으로 구성한 **표시 형식 예시**이며 새 앱의 실행 결과가 아니다. deg/s는 °/s와 같은 단위다.

```text
                       |           Acceleration (g) |   Angular velocity (deg/s)
 No.        Seq   Skip |        X        Y        Z |        X        Y        Z
   1        123      0 |   +0.104   -0.039   -0.977 |   -2.626   -0.969   +0.855
```

g는 중력가속도를 기준으로 한 가속도 단위이고 정지 상태에도 중력 성분이 포함된다. 자이로 출력은 회전 속도이며 현재 기울기 각도나 공간상의 위치가 아니다. 이 변경은 단위 환산·표 정렬이며 필터링·bias 제거·정확도 보정은 수행하지 않는다.

커널의 INIT 로그는 `accel range=+/-2 g, gyro range=+/-250 deg/s`로 바꿨다. 이는 순간 측정값이 아니라 설정한 측정 범위다. PROBE·CHAR·REMOVE는 장치 수명 로그로 유지하고 샘플을 dmesg에 중복 출력하지 않는다.

출력은 OPEN → READ → CLOSE 단위로 구분한다. 커널 dmesg는 장치 수명·IRQ 오류, 앱 표는 샘플 확인용이다. SAMPLE_COUNT=20은 검증 실행을 유한하게 끝내기 위한 값이고 read 자체의 횟수 제한은 아니다. 공칭100Hz에서20개를 받으면 이전100ms 대기 버전보다 빨리 끝날 수 있다. 약0.2초는 대략적인 예상일 뿐 실행 시간 보장이 아니다. 앱을 다시 실행해도 모듈/overlay 재적용은 필요 없다.

지금은 IRQ에서 수집한 **최신 한 샘플**을 앱이 받는다. 소프트웨어 큐나 센서 FIFO는 없으므로 느린 앱의 모든 데이터를 보존하지 않는다. 센서 준비·IRQ 처리·앱 전달 사이의 지연, 실제 샘플 시각과 정확한 도착 간격은 별도 검증 대상이다. 타임스탬프는 아직 공유 구조체에 포함하지 않았다.

## 헷갈리는 개념

| 대상 | 이번 실습의 의미 |
| --- | --- |
| `i2c-bcm2835` | Pi의 I2C 컨트롤러를 제어하는 기존 드라이버 |
| `mpu6050_drv.ko` | 주소 0x68의 센서 식별값을 읽는 직접 작성한 모듈 |
| `mpu6050-study` | 등록한 I2C 드라이버 이름 |
| `1-0068` | 버스 1, 7비트 주소 0x68인 I2C client 장치 |
| `/dev/i2c-1` | i2c-dev가 제공하는 사용자 공간 버스 접근 노드 |
| `/dev/mpu6050` | 이번 센서 드라이버가 공개하는 raw 한 샘플 read 인터페이스 |
| `reg = <0x68>` | 센서의 버스 주소. WHO_AM_I 레지스터 번호가 아님 |
| 레지스터 `0x75`의 값 `0x68` | 식별 응답. AD0로 통신 주소를 0x69로 바꿔도 식별값은 그대로 |

센서가 실제 배선되어 응답해도 DT 등으로 client를 생성하지 않았다면 `1-0068`은 없을 수 있다. 반대로 DT에 client를 선언해 sysfs 장치가 생겨도 센서의 실제 응답이나 probe 성공은 별도로 확인해야 한다.

이번에는 miscdevice를 통한 문자 인터페이스와 전용 앱이 있다. misc 등록·해제가 노드 수명을 관리하므로 수동 mknod나 rm은 하지 않는다. 드라이버 바인딩 중에는 같은 센서를 `i2ctransfer`로 직접 제어하지 않는다. 강제 접근 옵션으로 우회하지 않는다. 기본 개념은 [문자 디바이스 문서](../char_device/char-device.md)의 장치 노드 설명과 함께 비교한다.

AD0 외부 선의 필요 여부는 기판의 기본 LOW 보장 여부에 달려 있다. 이번 사용자 실측은 주소 `0x68`에서 응답한 사실을 확인한다. 외부 AD0 선 연결 여부나 기판 풀다운 회로를 이 결과만으로 단정하지 않는다.

## 참고 코드와의 차이

VEDA의 `임베디드리눅스/강의자료/임베디드리눅스1.pdf` 24~27쪽은 앞서 확인한 DT 구조·속성·compatible/reg 개념의 복습 자료다. `리눅스프로그래밍/강의자료/I2C_라즈베리파이.pdf`도 저장소에 있지만, 이번 구현과 대응하는 본문·예제는 아직 대조하지 않았다. 수업 코드와 특정 API가 같거나 다르다고 추정하지 않는다.

직접 비교한 대상은 현재 커널의 [inv_mpu_i2c.c](../../external/linux/drivers/iio/imu/inv_mpu6050/inv_mpu_i2c.c) `inv_mpu_probe()`와 드라이버 등록부다. 기존 드라이버는 여러 칩을 지원하며 `devm_regmap_init_i2c()`와 공통 코어를 통해 초기화·IIO 기능으로 연결한다. 이번에는 식별·설정에는 byte-data helper, 한 샘플에는 I2C block-read helper를 사용하고 각 API의 기능을 확인한다. 기존 코어의 `inv_mpu6050_sensor_show()`는 regmap으로 축 데이터를 읽고 big-endian 16비트를 부호 있게 해석한다. 이번 구현은 직접 받은 u8 배열에 get_unaligned_be16과 s16 변환을 적용한다. 기존 드라이버의 식별 후 리셋·100ms 대기와 오류 시 power-off 흐름도 참고했다. 다중 칩별 기동 시간·runtime PM 전체를 복제하지 않고 이번 센서의 초기화와 슬립 전환으로 범위를 제한했다. regmap·IIO는 필요할 때 추가한다. IRQ 스레드와 ONESHOT은 현재 커널의 inv_mpu_trigger.c도 사용한다. 기존 드라이버는 IIO 트리거와 타임스탬프로 연결하지만 현재는 상태 해제 뒤 샘플 읽기·최신 보관·wait queue 깨우기까지 구현했다. IIO나 FIFO를 복제한 것은 아니다. 기존 드라이버를 수정하거나 전체 복사하지 않았다.

API 근거는 같은 소스의 `include/linux/i2c.h`, `drivers/i2c/i2c-core-of.c`와 `Documentation/i2c/smbus-protocol.rst`다. 식별·설정 근거는 [제조사 Register Map §4.2~4.5·4.14~4.19·4.28·4.29·4.32](https://invensense.tdk.com/wp-content/uploads/2015/02/MPU-6000-Register-Map1.pdf)다.

## 빌드·배포·실행·정리

아래는 전체 재현 순서다. 한꺼번에 실행하지 않고 **빌드 결과 → 전송 → 드라이버 등록 → overlay 적용·초기화 → 해제**를 사용자와 함께 확인한다. 부팅 설정 변경·커널 재빌드·재부팅은 필요하지 않다.

### 1. WSL · 예제 디렉터리 · 빌드

선행 조건: 앞서 완성한 커널 빌드 결과·Module.symvers와 ARM64 GCC, 호스트 dtc가 있고 SSH 별칭 `pi`가 설정되어 있어야 한다.

```bash
cd /home/nakta/bspworkspace/bsp-study/examples/mpu6050
make
file mpu6050_drv.ko mpu6050_app
modinfo -F vermagic ./mpu6050_drv.ko
modinfo -F alias ./mpu6050_drv.ko
```

기대값은 ARM aarch64 형식과 `6.18.59-v8-bsp-study01`로 시작하는 vermagic, `nakta,mpu6050-study`의 OF 별칭 및 `i2c:mpu6050-study`다. 별칭의 전체 표시 형태·순서는 출력으로 확인한다.

### 2. WSL · 같은 예제 디렉터리 · 전송

선행 조건: 직전 빌드 성공과 모듈·overlay·앱 세 산출물 존재. 새 WSL 터미널에서도 먼저 같은 디렉터리로 이동한다.

```bash
cd /home/nakta/bspworkspace/bsp-study/examples/mpu6050
ssh pi 'mkdir -p ~/bsp/modules ~/bsp/overlays ~/bsp/apps'
make deploy
```

### 3. Pi · 홈 디렉터리 · 버전과 점유 확인

선행 조건: 전원 분리 상태에서 INT → 물리 11번(GPIO17) 배선을 완료한 뒤 부팅·SSH 접속, 새 모듈과 dtbo 전송 완료. 센서를 직접 읽는 다른 앱은 종료한 상태로 진행한다.

```bash
cd ~
uname -r
modinfo -F vermagic ~/bsp/modules/mpu6050_drv.ko
sudo dtoverlay -l
ls -ld /sys/bus/i2c/devices/1-0068
ls -l /sys/bus/i2c/devices/1-0068/driver
```

첫 실행에는 `1-0068` 장치와 driver 링크가 없을 것으로 예상한다. 이미 존재하면 어떤 overlay·장치·드라이버가 만든 것인지 확인하고 진행한다. 이전 실습 버전을 교체하는 경우 앱을 종료하고 이 문서 마지막의 overlay 제거·rmmod를 먼저 수행한 뒤 새 모듈을 로드한다. 같은 주소에 노드를 중복 생성하지 않는다. 버전 불일치도 먼저 해결한다.

### 4. Pi · 모듈 디렉터리 · 드라이버 등록

```bash
cd ~/bsp/modules
sudo insmod ./mpu6050_drv.ko
lsmod | grep '^mpu6050_drv '
ls -ld /sys/bus/i2c/drivers/mpu6050-study
sudo dmesg | grep -F 'mpu6050-study'
```

아직 client 장치가 없다면 새 PROBE 로그가 없는 것이 예상 동작이다. 예전 로그가 남을 수 있으므로 시간과 내용을 함께 본다.

### 5. Pi · overlay 디렉터리 · 장치 생성과 통신 확인

선행 조건: 드라이버 등록 완료, 같은 주소의 기존 client 없음. 처음에는 이미 확인한 주소 `0x68`을 사용한다.

```bash
cd ~/bsp/overlays
sudo dtoverlay -d "$PWD" mpu6050-overlay
sudo dtoverlay -l
tr '\0' '\n' < /proc/device-tree/soc/i2c@7e804000/mpu6050@68/compatible
readlink -e /sys/bus/i2c/devices/1-0068/driver
ls -l /dev/mpu6050
grep -w mpu6050 /proc/misc
sudo dmesg | grep -F 'mpu6050-study'
```

아래는 **예상 로그**이며 실측 결과가 아니다.

```text
mpu6050-study 1-0068: [PROBE] addr=0x68, WHO_AM_I=0x68
mpu6050-study 1-0068: [INIT] reg=0x6b, value=0x01
mpu6050-study 1-0068: [INIT] reg=0x6c, value=0x00
mpu6050-study 1-0068: [INIT] reg=0x1b, value=0x00
mpu6050-study 1-0068: [INIT] reg=0x1c, value=0x00
mpu6050-study 1-0068: [INIT] reg=0x1a, value=0x03
mpu6050-study 1-0068: [INIT] reg=0x19, value=0x09
mpu6050-study 1-0068: [INIT] reg=0x37, value=0x20
mpu6050-study 1-0068: [INIT] ready: accel range=+/-2 g, gyro range=+/-250 deg/s
mpu6050-study 1-0068: [INIT] reg=0x38, value=0x01
mpu6050-study 1-0068: [IRQ] irq=<Linux IRQ 번호>, data-ready nominal=100 Hz
mpu6050-study 1-0068: [CHAR] /dev/mpu6050 ready: IRQ latest-sample read
```

driver 링크의 예상 대상은 `/sys/bus/i2c/drivers/mpu6050-study`다. overlay 추가 성공뿐 아니라 링크·새 PROBE 로그·INIT 설정값·ready·IRQ·CHAR와 노드 존재를 함께 확인한다. 식별 로그가 나와도 초기화·IRQ·misc 등록 도중 실패하면 바인딩되지 않는다. 현재 버전은 probe에서 DATA를 출력하지 않는다.

### 6. Pi · 홈 디렉터리 · IRQ 횟수 확인

선행 조건: INT 배선·새 버전 probe 성공과 IRQ 등록 로그 확인. 앱은 아직 실행하지 않아도 된다.

```bash
cd ~
pinctrl get 17
gpioinfo | grep -E 'gpiochip|GPIO17'
grep -F 'mpu6050-data-ready' /proc/interrupts
sleep 2
grep -F 'mpu6050-data-ready' /proc/interrupts
```

두 시점의 CPU별 횟수 합이 증가하는지 본다. 공칭 100Hz이므로 2초 동안 대략 200회를 예상할 수 있지만 처리 지연·관측 구간·래치 병합에 따라 달라지며 이를 엄격한 합격 숫자로 쓰지 않는다. GPIO17/물리 11과 Linux IRQ 번호는 별개다. 행이 없으면 IRQ 등록 실패부터, 횟수가 증가하지 않으면 실제 배선·극성·INT_ENABLE과 상태 읽기 로그부터 확인한다. 성공했다고 미리 기록하지 않는다.

### 7. Pi · 앱 디렉터리 · 반복 읽기

선행 조건: 새 버전 바인딩과 /dev/mpu6050 노드 생성 확인. 모듈과 앱은 순번을 포함한16바이트 구조체 버전으로 함께 갱신한다. 같은 센서를 i2ctransfer로 직접 접근하지 않는다.

```bash
cd ~/bsp/apps
sudo ./mpu6050_app
echo $?
```

OPEN → blocking READ 표20줄 → CLOSE와 종료 상태0이 기대된다. Seq가 증가하고 Skip으로 게시 순번 차이를 관찰한다. 가속도 g·각속도 deg/s가 축별 표로 표시되며 고정된 예상 숫자는 없다. 우선 가만히 두고 출력이 계속 수신되는지 본다. 필요하면 앱 실행 중 모듈의 노출 도체가 다른 물체에 닿지 않게 자세를 천천히 바꿔 값 변화를 확인한다. 앱을 다시 실행해도 overlay 재적용은 필요하지 않다. 아직 사용자 실행 결과는 검증 현황과 구분한다.

### 8. Pi · overlay → 모듈 디렉터리 · 해제

```bash
cd ~/bsp/overlays
sudo dtoverlay -r mpu6050-overlay
sudo dtoverlay -l
ls -ld /sys/bus/i2c/devices/1-0068
ls -l /dev/mpu6050
grep -F 'mpu6050-data-ready' /proc/interrupts
sudo dmesg | grep -F 'mpu6050-study'
ls -ld /sys/bus/i2c/drivers/mpu6050-study

cd ~/bsp/modules
sudo rmmod mpu6050_drv
lsmod | grep '^mpu6050_drv '
ls -ld /sys/bus/i2c/drivers/mpu6050-study
```

앱이 종료된 뒤 정리한다. overlay 제거 뒤에는 /dev/mpu6050과 client 장치가 사라지고 성공적으로 바인딩됐던 경우 REMOVE의 data-ready count 로그가 남는다. /proc/interrupts의 해당 IRQ 행도 없어져야 한다. 이때 드라이버 디렉터리는 남으며 rmmod 후 사라진다. 없는 경로를 조회한 `ls` 오류는 해당 정리 단계의 예상 결과다. 교체 빌드 후 재실행할 때도 이 순서로 기존 overlay·모듈을 해제한 뒤 새 파일을 로드한다.

| 반복·움직임·해제 실측 | 앱 재실행에서 흔드는 동안 raw 20행·CLOSE·종료 상태 0 확인. overlay 제거 후 /dev/mpu6050 및 1-0068 부재·REMOVE(5015.346503), rmmod 후 lsmod 출력 없음 확인 |

사용자 공간 읽기와 별도로, **초기화 추가 전 식별 전용 모듈**에서도 다음 로그를 사용자가 확인했다.

```text
[ 1241.154432] mpu6050-study 1-0068: [PROBE] addr=0x68, WHO_AM_I=0x68
[ 1308.142346] mpu6050-study 1-0068: [REMOVE] detached
```

초기화 버전에서 별도로 받은 대표 로그는 다음과 같다. 레지스터 네 개의 readback·driver 링크도 사용자 출력으로 확인했다.

```text
[ 1964.338764] mpu6050-study 1-0068: [INIT] ready: gyro=250 dps, accel=2 g
[ 2029.226687] mpu6050-study 1-0068: [REMOVE] detached
```

과거 probe 한 샘플 버전에서는 다음 실측을 받았다. 사용자는 기판을 평평하게 두지 않고 뒤집힌 채 비스듬히 놓았다고 설명했다. 정확한 기울기·축 방향·읽는 순간의 움직임은 측정하지 않았다.

```text
[ 2412.772622] mpu6050-study 1-0068: [DATA] accel raw: x=-7588, y=-4320, z=-12400
[ 2412.772629] mpu6050-study 1-0068: [DATA] gyro raw: x=-312, y=-81, z=45
```

데이터시트의 현재 범위 감도는 가속도 16384 LSB/g, 자이로 131 LSB/(°/s)다. 수동으로 환산하면 가속도는 약 (-0.463, -0.264, -0.757)g, 자이로는 (-2.382, -0.618, 0.344)°/s다. 근거: [제조사 Product Specification §6.1·6.2](https://product.tdk.com/system/files/dam/doc/product/sensor/mortion-inertial/imu/data_sheet/mpu-6000-datasheet1.pdf). 이는 당시 raw 로그에 대한 수동 환산이다. 현재 앱의 단위 표시를 실행해 확인한 결과는 아니다.

비스듬한 자세에서는 중력 성분이 여러 축에 나뉠 수 있지만, 자세 변경만으로 벡터 크기가 달라지는 것은 아니다. 이 샘플의 가속도 크기는 약 0.926g로 1g와 차이가 있다. 자세 설명과 단일 샘플만으로 정확도 정상·불량 또는 원인을 확정하지 않는다. 자이로 역시 정지했다면 0에 가까운 것이 기대되지만, 현재 비영점 값이 오프셋인지 읽는 순간의 움직임인지 한 번의 출력으로 구분할 수 없다. 이번 검증 범위는 실제 센서의 14바이트 읽기·부호 해석·raw 출력과 바인딩까지다.

그다음 사용자 보고에서는 핀 돌출부가 위쪽, LED가 아래쪽인 자세에서 accel=(1708, -644, -16000), gyro=(-344, -127, 112)를 받았다. 가속도는 약 (0.104, -0.039, -0.977)g, 크기 약 0.983g다. 정확한 칩 축 표기·각도·반복 오프셋 검증은 수행하지 않았다.

위 결과는 모두 과거 probe 한 샘플 버전의 로그다. 그 버전에서는 새 자세의 데이터를 읽으려면 overlay를 재적용해야 했지만 현재 코드는 앱의 매 read마다 새로 읽으므로 그 절차가 필요하지 않다. 과거 결과와 현재 문자 인터페이스의 실행 근거를 구분한다. 실제 장애는 아직 보고되지 않았으므로 예상 오류를 트러블슈팅 이력으로 만들지 않는다.


단위 표시 추가 전 raw 출력 문자 인터페이스에서는 아래 결과를 별도로 확인했다. 앱의 20줄 전체가 수신됐으며 대표 첫 줄·마지막 줄만 보존한다. 생략 표시는 실제 출력 문자가 아니다.

```text
[ 4714.674150] mpu6050-study 1-0068: [CHAR] /dev/mpu6050 ready
crw------- 1 root root 10, 266 Nov  5 19:02 /dev/mpu6050

=== OPEN ===
device: /dev/mpu6050
=== READ: 20 samples, 100 ms wait ===
01 accel raw: x=-5340, y=-1540, z=-14336 | gyro raw: x=-313, y=-113, z=76
… 중간 18줄 생략 …
20 accel raw: x=-5316, y=-1468, z=-14532 | gyro raw: x=-322, y=-71, z=51
=== CLOSE ===
0
```

이 결과는 앱 요청 → 커널 센서 읽기 → 사용자 복사 → 반복 출력·종료까지의 정상 경로를 확인한다. 각 회차 값이 달라지는 것을 관측했지만 모든 내부 샘플의 수집·정확한 10Hz·정확도 보정을 검증한 것은 아니다. 이번 실행의 정확한 자세는 별도 보고되지 않아 과거 자세와 같다고 추정하지 않는다.


앱을 다시 실행해 흔든 실측에서도 20회 수신·정상 종료를 확인했다. 예를 들어 3회차 gyro Y=-22768, 13회차 gyro Z=28474처럼 정지 때보다 큰 변화가 관측됐다. 이후 overlay 제거로 노드와 client가 사라지고 `[ 5015.346503] ... [REMOVE] detached`가 출력됐으며 rmmod 후 lsmod 조회도 비어 있었다. 이 결과는 이전 raw 출력 버전의 재실행·움직임 반응·정리를 확인하며 새 단위 표시의 보드 검증과 구분한다.


단위 표시 버전에서도 별도로 실행 결과를 받았다. 첫 실행은 값이 비교적 일정했고 두 번째는 큰 변화가 있었다. 정확한 움직임·자세를 수치로 측정한 것은 아니다. 대표 출력은 다음과 같다.

```text
[ 5997.471796] mpu6050-study 1-0068: [INIT] ready: accel range=+/-2 g, gyro range=+/-250 deg/s
[ 5997.472079] mpu6050-study 1-0068: [CHAR] /dev/mpu6050 ready

첫 실행 1행: accel(g)=(-0.538, -0.020, -0.756), gyro(deg/s)=(-2.412, -0.832, +0.557)
두 번째 실행 10행: accel(g)=(-0.520, +0.131, -0.722), gyro(deg/s)=(+187.359, -250.137, -102.366)
두 실행 모두 20행 출력 후 CLOSE, 종료 상태 0
```

두 번째 실행 10행의 gyro Y=-250.137은 -32768/131=-250.137404...의 소수점 셋째 자리 표시와 일치한다. 현재 raw는 signed 16비트이므로 음수 하한에 해당하며 ±250°/s 범위의 포화 가능성이 있다. 표시 숫자가 250을 약간 넘는 것만으로 변환 오류라고 판단하지 않는다. 이 기록은 포화 가능성을 보여주며 실제 각속도·정확도·포화 지속 시간을 측정한 것은 아니다. 빠른 회전을 대상으로 범위를 늘릴 경우 드라이버 FS_SEL뿐 아니라 앱의 감도 상수와 범위 안내도 함께 변경해야 한다. 현재 범위와 코드는 그대로 유지했다.


IRQ 상태 처리와 앱 폴링을 병행하던 이전 버전의 사용자 실측은 다음과 같다.

```text
61:       1851          0          0          0 pinctrl-bcm2835  17 Level     mpu6050-data-ready
61:       2051          0          0          0 pinctrl-bcm2835  17 Level     mpu6050-data-ready
[ 1033.129819] mpu6050-study 1-0068: [IRQ] irq=61, data-ready nominal=100 Hz
[ 1033.129832] mpu6050-study 1-0068: [CHAR] /dev/mpu6050 ready
[ 1236.129090] mpu6050-study 1-0068: [REMOVE] detached, data-ready count=20268
```

첫 두 조회 사이에는 사용자가 sleep 2를 실행했고 차이는 200회다. 이는 공칭100Hz와 부합하는 관측이며 정확한 간격·모든 내부 샘플 보존 검증은 아니다. GPIO17은 하드웨어 line, 61은 이번 Linux IRQ 매핑 결과다. 61을 드라이버나 재현 명령의 고정값으로 쓰지 않는다.

IRQ가 활성화된 상태에서도 앱이 표 20행을 출력하고 CLOSE·종료 상태 0을 반환했다. 이후 IRQ 조회는 누적13982였지만 앞선 조회와의 정확한 경과 시간은 없어 그 값으로 주파수를 계산하지 않았다. 샘플은 앱 read에서 읽은 것이며 IRQ에서 전달한 결과가 아니다.

overlay 제거 뒤 grep한 mpu6050-data-ready IRQ 행은 출력이 없었고 /dev/mpu6050은 존재하지 않았다. REMOVE의 Data Ready 상태 처리 누적은20268이며 rmmod 뒤 lsmod 조회도 비었다. 이는 정상 등록·IRQ 처리·폴링 공존·해제를 확인한다. 초기화 레지스터 readback 전문은 이번 실행 출력에 포함되지 않았으며 과거 결과와 구분한다. 열린 파일을 유지한 제거·I2C 실패·실제 수집률/타임스탬프·IRQ 기반 샘플 전달은 이번 실측에 포함하지 않는다.


현재 IRQ 샘플 전달 버전에서 앱은 `20 IRQ samples, blocking read`를 출력하고 Seq2632~2651을20회 연속 수신했다. Skip은 모든 행0이고 CLOSE 후 종료 상태0이었다. 대표값은 첫 행 accel=(-0.441,-0.052,-0.815)g/gyro=(-2.649,-1.443,+0.603)deg/s, 마지막 행 accel=(-0.440,-0.053,-0.819)g/gyro=(-2.427,-0.687,+0.542)deg/s다. 앱 실행 전부터 수집하므로 첫 Seq가1일 필요는 없다. Skip=0은 관측한 게시 순번 사이의 연속성을 뜻하며 센서 내부 샘플 전체의 보존·정확한 주기 검증은 아니다.

앱 실행 후 재조회에서는 Linux IRQ61의 누적35514와 아래 등록 로그가 확인됐다. 최초 조회에 일부 출력이 없었던 원인은 확정하지 않았다.

```text
[10728.257762] mpu6050-study 1-0068: [IRQ] irq=61, data-ready nominal=100 Hz
[10728.257769] mpu6050-study 1-0068: [CHAR] /dev/mpu6050 ready: IRQ latest-sample read
[11939.417180] mpu6050-study 1-0068: [REMOVE] detached, data-ready count=120925
```

앱이 종료된 상태에서 overlay를 제거하자 IRQ 행 조회는 비었고 /dev/mpu6050은 없었다. 이어 rmmod가 오류 없이 완료됐으며 lsmod 조회도 비었다. 현재 버전의 기본 수집·앱 전달·정상 해제 경로를 확인한 것이며 대기 중 read를 유지한 제거·동시 read·실패 경로·시간 정확도는 별도 미검증이다.
