## 구현 범위

소스는 [mpu6050_drv.c](mpu6050_drv.c), [mpu6050-overlay.dts](mpu6050-overlay.dts), [Makefile](Makefile)이다. 기존 커널의 I2C 컨트롤러 드라이버를 이용해 직접 작성한 센서 드라이버에서 식별값을 읽는다.

현재 구현은 **DT 장치 선언 → 드라이버 매칭 → probe에서 WHO_AM_I 확인 → remove**까지다. 센서 초기화·가속도/자이로 측정·IRQ·FIFO·IIO·사용자 앱은 아직 구현하지 않았다. WHO_AM_I 읽기는 통신 기준선이며 측정 기능의 정상 동작까지 의미하지 않는다.

대상은 Pi 4, 커널 `6.18.59-v8-bsp-study01`, 소스 커밋 `b3495ea401d709af0701a85babcba5e3d788a602`이다. [커널 구축](../../docs/kernel-build.md)에서 준비한 WSL 빌드 디렉터리 `out/kernel-rpi4`를 그대로 사용한다. 실제 배선은 [bringup](../../docs/bringup.md#모듈과-핀-연결표)에서 관리한다.

## 전체 실행 흐름

1. 사용자가 `insmod mpu6050_drv.ko`를 실행하면 `module_i2c_driver()`가 마련한 초기화 경로에서 I2C 드라이버를 등록한다. 센서 DT 노드가 아직 없으면 probe는 호출되지 않는다.
2. 사용자가 runtime overlay를 추가하면 기존 `i2c1` 아래에 `mpu6050@68` 노드가 붙는다. I2C 코어가 이를 주소 `0x68`의 `struct i2c_client`로 등록한다. sysfs 장치 이름은 `1-0068`이다.
3. I2C 버스의 매칭 과정이 노드의 compatible과 드라이버의 OF 테이블을 비교한다. 일치하면 커널이 `mpu6050_probe(client)`를 호출한다.
4. probe는 전송 기능을 확인하고 `i2c_smbus_read_byte_data()`로 레지스터 `0x75`를 읽는다. I2C 코어와 기존 `i2c-bcm2835` 컨트롤러 드라이버가 실제 버스 전송을 수행한다.
5. 읽은 값이 `0x68`이면 성공 로그와 함께 0을 반환하고 바인딩된다. 전송 실패·식별 불일치이면 음수 오류를 반환한다. DT 장치가 존재하는 것과 probe 성공은 별개다.
6. overlay를 제거하면 센서 장치가 제거되면서 바인딩된 드라이버의 `mpu6050_remove()`가 호출된다. 드라이버 등록은 남는다. 이어서 `rmmod`하면 드라이버 등록도 해제된다.

순서를 반대로 해서 장치가 먼저 존재해도 드라이버 등록 시 매칭될 수 있다. 여기서는 이전 [platform 실습](../platform_device/platform-device.md)과 비교하기 위해 드라이버를 먼저 등록한다.

## 코드 해설

### 1. 센서를 기존 I2C 버스에 선언

```dts
target = <&i2c1>;

__overlay__ {
	#address-cells = <1>;
	#size-cells = <0>;
	status = "okay";

	mpu6050@68 {
		compatible = "nakta,mpu6050-study";
		reg = <0x68>;
		status = "okay";
	};
};
```

`&i2c1`은 기존 DT 심볼로, 이번 배선의 GPIO2/3을 사용하는 컨트롤러를 가리킨다. platform 예제는 루트에 장치를 추가했지만 이번 센서는 **I2C 컨트롤러의 자식**이다. 부모 버스가 자식 장치를 어떻게 해석할지 결정한다.

이 I2C 버스의 `reg`는 CPU 메모리 주소가 아니라 **7비트 I2C 주소**다. `#address-cells = <1>`은 주소를 한 셀로 표현하고 `#size-cells = <0>`은 MMIO 영역 크기를 붙이지 않는다는 뜻이다. 노드의 `@68`과 `reg`를 맞춘다. DT 선언만으로 센서의 AD0 전압이나 실제 주소가 바뀌지는 않는다.

`nakta,mpu6050-study`는 학습 드라이버를 선택하기 위한 로컬 compatible이다. 공식 MPU6050 binding이나 제품용 식별자가 아니다. 기존 드라이버용 `invensense,mpu6050`을 함께 적지 않는다. 이후 기존 IIO 드라이버로 전환할 때는 이 overlay와 학습 드라이버를 해제하고 해당 binding에 맞춘다.

### 2. 필요한 전송 기능 확인

```c
if (!i2c_check_functionality(client->adapter,
			     I2C_FUNC_SMBUS_READ_BYTE_DATA))
	return dev_err_probe(&client->dev, -EOPNOTSUPP,
			     "[PROBE] byte data transfer unsupported\n");
```

`client`는 커널이 전달하는 현재 센서 장치의 포인터다. `client->adapter`는 이 센서가 연결된 버스이고, `client->addr`에는 DT에서 읽은 주소가 있다. 사용자 코드처럼 `/dev/i2c-1`을 open하거나 주소를 다시 지정할 필요가 없다.

`I2C_FUNC_SMBUS_READ_BYTE_DATA`는 레지스터 번호 한 바이트를 지정하고 데이터 한 바이트를 읽는 기능이다. 이번에는 데이터 쓰기를 하지 않으므로 읽기 기능만 요구한다. 컨트롤러가 SMBus 전용 하드웨어일 필요는 없다. I2C 코어가 지원되는 일반 I2C 전송으로 해당 동작을 구현할 수도 있다. 지원 여부를 확인한 뒤 API를 쓴다.

`dev_err_probe()`는 장치 정보와 오류 메시지를 출력하고 전달한 오류 코드를 반환한다. `&client->dev`는 구조체 안의 `struct device` 멤버 주소다. 여기서는 지원하지 않는 전송 방식에 `-EOPNOTSUPP`를 반환한다.

### 3. WHO_AM_I 읽기와 반환값 검사

```c
ret = i2c_smbus_read_byte_data(client, MPU6050_REG_WHO_AM_I);
if (ret < 0)
	return dev_err_probe(&client->dev, ret,
			     "[PROBE] failed to read WHO_AM_I\n");

if (ret != MPU6050_WHO_AM_I)
	return dev_err_probe(&client->dev, -ENODEV,
			     "[PROBE] unexpected WHO_AM_I=0x%02x\n",
			     ret);

dev_info(&client->dev, "[PROBE] addr=0x%02x, WHO_AM_I=0x%02x\n",
	 client->addr, ret);
return 0;
```

`MPU6050_REG_WHO_AM_I`는 `0x75`, `MPU6050_WHO_AM_I`는 예상 내용인 `0x68`이다. 앞서 실행한 `i2ctransfer -y 1 w1@0x68 0x75 r1`과 같은 레지스터 읽기 목적을 커널 API로 수행한다. 측정 설정을 바꾸거나 센서를 깨우는 코드는 없다.

이 API는 성공 시 **0~255의 데이터**, 실패 시 음수 오류를 반환한다. 따라서 `ret`는 `int`로 받고 음수부터 검사한다. 처음부터 `u8`로 받으면 음수 오류가 잘려 데이터처럼 보일 수 있다. 정상 통신했어도 식별값이 다르면 `-ENODEV`로 probe를 실패시킨다. 이 단계에서는 예상 식별값 확인까지만 하며 같은 값을 쓰는 모든 칩을 엄밀히 구분하는 구현은 아니다.

`%02x`는 16진수를 최소 두 자리로 출력한다. probe의 최종 `return 0`은 읽은 데이터가 아니라 **드라이버 초기 연결 성공**을 뜻한다.

### 4. 매칭 테이블과 드라이버 등록

```c
static const struct of_device_id mpu6050_match[] = {
	{ .compatible = "nakta,mpu6050-study" },
	{},
};
MODULE_DEVICE_TABLE(of, mpu6050_match);

static const struct i2c_device_id mpu6050_ids[] = {
	{ "mpu6050-study", 0 },
	{},
};
MODULE_DEVICE_TABLE(i2c, mpu6050_ids);
```

OF 테이블은 DT compatible 매칭에 쓴다. I2C ID 테이블은 이름 기반 매칭과 I2C 모듈 별칭을 제공한다. 여기서는 DT를 사용하고 두 식별자 모두 실습 전용 이름으로 맞췄다. 두 테이블의 끝에는 종료 표시인 빈 항목이 있다. `static`은 이 소스 파일 안에서만 이름을 사용하게 하고 `const`는 테이블 내용을 수정하지 않도록 한다.

`MODULE_DEVICE_TABLE()`은 빌드 시 장치 별칭 정보를 모듈에 포함하게 한다. `modinfo -F alias`로 확인할 수 있다. 별칭이 있다고 전송한 파일이 자동으로 설치·로드되는 것은 아니다. 이번 실습에서는 `~/bsp/modules/`의 파일을 `insmod`로 직접 로드한다.

```c
static struct i2c_driver mpu6050_driver = {
	.probe = mpu6050_probe,
	.remove = mpu6050_remove,
	.id_table = mpu6050_ids,
	.driver = {
		.name = "mpu6050-study",
		.of_match_table = mpu6050_match,
	},
};
module_i2c_driver(mpu6050_driver);
```

`.probe = mpu6050_probe`는 함수를 지금 실행하는 표현이 아니라 콜백 주소를 등록하는 초기화다. 나중에 I2C 코어가 호출한다. 현재 6.18 소스의 선언에 맞춰 probe는 `int (struct i2c_client *)`, remove는 `void (struct i2c_client *)` 형식이다. 예전 자료의 probe 인자나 remove 반환형을 그대로 섞지 않는다.

`module_i2c_driver()`는 모듈 로드 시 드라이버 등록, 해제 시 등록 해제를 수행할 init/exit 경로를 만든다. 문자 디바이스의 `file_operations`를 등록하는 것과 다른 역할이다.

### 5. 해제와 자원

```c
static void mpu6050_remove(struct i2c_client *client)
{
	dev_info(&client->dev, "[REMOVE] detached\n");
}
```

이번 드라이버는 별도 메모리·IRQ·작업 큐·sysfs 속성을 만들지 않고 probe에서 한 번만 읽는다. 그래서 해제 로그 외의 정리 작업이 없다. 센서 장치 자체는 I2C 코어가 관리하므로 여기서 직접 free하지 않는다. 실패한 probe를 정리하기 위해 remove가 호출된다고 기대해서도 안 된다. 이후 자원을 추가하면 실패 경로와 remove를 함께 설계한다.

### 6. Makefile

기존 [platform Makefile 해설](../platform_device/platform-device.md)의 Kbuild 분기·크로스 컴파일·호스트 dtc 사용 방식을 유지했다. `obj-m := mpu6050_drv.o`가 `.ko` 이름을 정하며, `all`은 `modules`와 `overlay`를 만든다. overlay 규칙은 DTS를 의존성으로 두고 `dtc -@`로 DT 심볼 참조에 필요한 정보를 포함한다.

`KDIR` 기본값은 현재 예제 디렉터리에서 `../../out/kernel-rpi4`를 절대 경로로 계산한다. `ARCH=arm64`, `CROSS_COMPILE=aarch64-linux-gnu-`, `LOCALVERSION=`를 전달해 같은 커널 빌드 결과를 참조한다. **dtc는 WSL에서 실행하는 호스트 프로그램**이며 ARM64 타깃 실행 파일이 아니다.

`make deploy`는 이미 만든 `.ko`와 `.dtbo`를 전송만 한다. 자동 빌드·모듈 로드·overlay 적용은 하지 않는다. `clean`은 이 예제의 생성물을 지우며 커널 전체를 재빌드하지 않는다.

## 헷갈리는 개념

| 대상 | 이번 실습의 의미 |
| --- | --- |
| `i2c-bcm2835` | Pi의 I2C 컨트롤러를 제어하는 기존 드라이버 |
| `mpu6050_drv.ko` | 주소 0x68의 센서 식별값을 읽는 직접 작성한 모듈 |
| `mpu6050-study` | 등록한 I2C 드라이버 이름 |
| `1-0068` | 버스 1, 7비트 주소 0x68인 I2C client 장치 |
| `/dev/i2c-1` | i2c-dev가 제공하는 사용자 공간 버스 접근 노드 |
| `reg = <0x68>` | 센서의 버스 주소. WHO_AM_I 레지스터 번호가 아님 |
| 레지스터 `0x75`의 값 `0x68` | 식별 응답. AD0로 통신 주소를 0x69로 바꿔도 식별값은 그대로 |

센서가 실제 배선되어 응답해도 DT 등으로 client를 생성하지 않았다면 `1-0068`은 없을 수 있다. 반대로 DT에 client를 선언해 sysfs 장치가 생겨도 센서의 실제 응답이나 probe 성공은 별도로 확인해야 한다.

이번에는 문자 디바이스를 만들지 않으므로 `mknod`, major/minor, 사용자 앱이 필요하지 않다. 드라이버 바인딩 중에는 같은 센서를 `i2ctransfer`로 직접 제어하지 않는다. 강제 접근 옵션으로 우회하지 않는다. 기본 개념은 [문자 디바이스 문서](../char_device/char-device.md)의 장치 노드 설명과 함께 비교한다.

AD0 외부 선의 필요 여부는 기판의 기본 LOW 보장 여부에 달려 있다. 이번 사용자 실측은 주소 `0x68`에서 응답한 사실을 확인한다. 외부 AD0 선 연결 여부나 기판 풀다운 회로를 이 결과만으로 단정하지 않는다.

## 참고 코드와의 차이

VEDA의 `임베디드리눅스/강의자료/임베디드리눅스1.pdf` 24~27쪽은 앞서 확인한 DT 구조·속성·compatible/reg 개념의 복습 자료다. `리눅스프로그래밍/강의자료/I2C_라즈베리파이.pdf`도 저장소에 있지만, 이번 구현과 대응하는 본문·예제는 아직 대조하지 않았다. 수업 코드와 특정 API가 같거나 다르다고 추정하지 않는다.

직접 비교한 대상은 현재 커널의 [inv_mpu_i2c.c](../../external/linux/drivers/iio/imu/inv_mpu6050/inv_mpu_i2c.c) `inv_mpu_probe()`와 드라이버 등록부다. 기존 드라이버는 여러 칩을 지원하며 `devm_regmap_init_i2c()`와 공통 코어를 통해 초기화·IIO 기능으로 연결한다. 이번에는 한 바이트 식별 읽기만 익히므로 SMBus byte-data helper를 사용하고, 그 API에 대응하는 기능만 확인한다. 블록 읽기·regmap·IRQ·IIO는 필요할 때 추가한다. 기존 드라이버를 수정하거나 전체 복사하지 않았다.

API 근거는 같은 소스의 `include/linux/i2c.h`, `drivers/i2c/i2c-core-of.c`와 `Documentation/i2c/smbus-protocol.rst`다. 식별 레지스터 근거는 [제조사 Register Map §4.32](https://invensense.tdk.com/wp-content/uploads/2015/02/MPU-6000-Register-Map1.pdf)다.

## 빌드·배포·실행·정리

아래는 전체 재현 순서다. 한꺼번에 실행하지 않고 **빌드 결과 → 전송 → 드라이버 등록 → overlay 적용 → 해제**를 사용자와 함께 확인한다. 부팅 설정 변경·커널 재빌드·재부팅은 필요하지 않다.

### 1. WSL · 예제 디렉터리 · 빌드

선행 조건: 앞서 완성한 커널 빌드 결과·Module.symvers와 ARM64 GCC, 호스트 dtc가 있고 SSH 별칭 `pi`가 설정되어 있어야 한다.

```bash
cd /home/nakta/bspworkspace/bsp-study/examples/mpu6050
make
file mpu6050_drv.ko
modinfo -F vermagic ./mpu6050_drv.ko
modinfo -F alias ./mpu6050_drv.ko
```

기대값은 ARM aarch64 형식과 `6.18.59-v8-bsp-study01`로 시작하는 vermagic, `nakta,mpu6050-study`의 OF 별칭 및 `i2c:mpu6050-study`다. 별칭의 전체 표시 형태·순서는 출력으로 확인한다.

### 2. WSL · 같은 예제 디렉터리 · 전송

선행 조건: 직전 빌드 성공과 두 산출물 존재. 새 WSL 터미널에서도 먼저 같은 디렉터리로 이동한다.

```bash
cd /home/nakta/bspworkspace/bsp-study/examples/mpu6050
ssh pi 'mkdir -p ~/bsp/modules ~/bsp/overlays'
make deploy
```

### 3. Pi · 홈 디렉터리 · 버전과 점유 확인

선행 조건: 배선 완료·전송 완료·SSH 접속. 센서를 직접 읽는 다른 앱은 종료한 상태로 진행한다.

```bash
cd ~
uname -r
modinfo -F vermagic ~/bsp/modules/mpu6050_drv.ko
sudo dtoverlay -l
ls -ld /sys/bus/i2c/devices/1-0068
ls -l /sys/bus/i2c/devices/1-0068/driver
```

첫 실행에는 `1-0068` 장치와 driver 링크가 없을 것으로 예상한다. 이미 존재하면 어떤 overlay·장치·드라이버가 만든 것인지 확인하고 진행한다. 같은 주소에 노드를 중복 생성하지 않는다. 버전 불일치도 먼저 해결한다.

### 4. Pi · 모듈 디렉터리 · 드라이버 등록

```bash
cd ~/bsp/modules
sudo insmod ./mpu6050_drv.ko
lsmod | grep '^mpu6050_drv '
ls -ld /sys/bus/i2c/drivers/mpu6050-study
sudo dmesg | grep -F 'mpu6050-study'
```

아직 client 장치가 없다면 새 PROBE 로그가 없는 것이 예상 동작이다. 예전 로그가 남을 수 있으므로 시간과 내용을 함께 본다.

### 5. Pi · overlay 디렉터리 · 장치 생성과 통신 확인

선행 조건: 드라이버 등록 완료, 같은 주소의 기존 client 없음. 처음에는 이미 확인한 주소 `0x68`을 사용한다.

```bash
cd ~/bsp/overlays
sudo dtoverlay -d "$PWD" mpu6050-overlay
sudo dtoverlay -l
tr '\0' '\n' < /proc/device-tree/soc/i2c@7e804000/mpu6050@68/compatible
readlink -e /sys/bus/i2c/devices/1-0068/driver
sudo dmesg | grep -F 'mpu6050-study'
```

아래는 **예상 로그**이며 실측 결과가 아니다.

```text
mpu6050-study 1-0068: [PROBE] addr=0x68, WHO_AM_I=0x68
```

driver 링크의 예상 대상은 `/sys/bus/i2c/drivers/mpu6050-study`다. overlay 추가 성공뿐 아니라 링크와 새 PROBE 로그를 함께 확인해 바인딩 성공을 판단한다.

### 6. Pi · overlay → 모듈 디렉터리 · 해제

```bash
cd ~/bsp/overlays
sudo dtoverlay -r mpu6050-overlay
sudo dtoverlay -l
ls -ld /sys/bus/i2c/devices/1-0068
sudo dmesg | grep -F 'mpu6050-study'
ls -ld /sys/bus/i2c/drivers/mpu6050-study

cd ~/bsp/modules
sudo rmmod mpu6050_drv
lsmod | grep '^mpu6050_drv '
ls -ld /sys/bus/i2c/drivers/mpu6050-study
```

overlay 제거 뒤에는 client 장치가 사라지고 성공적으로 바인딩됐던 경우 REMOVE 로그가 남는다. 이때 드라이버 디렉터리는 남으며 rmmod 후 사라진다. 없는 경로를 조회한 `ls` 오류는 해당 정리 단계의 예상 결과다. 교체 빌드 후 재실행할 때도 이 순서로 기존 overlay·모듈을 해제한 뒤 새 파일을 로드한다.
